# Alchemy

It instructs the agents that work on Alchemy; people read `README.md` and `INSTALL.md`. The agents keep it current, wording included. Pascal decides compilers, what counts as DONE, and deleting anything that cannot be restored; everything else goes ahead without asking, including fixing a check that wrongly blocks honest work as long as it still refuses everything it refused before.

Alchemy rebuilds Golden Sun: **The Broken Seal** (☀️, build `tbs`) and **The Lost Age** (⚓️, `tla`) byte for byte from readable C, assembly and editable assets, in Japanese, English, German, Spanish, French and Italian: twelve editions, `tbs-ja` to `tla-it`. Japanese releases are the source editions; localizations are measured differences.

Matching is finished: both games build byte for byte from source. How the code was matched, measured and adopted, and the rules on what counts and how unfinished work is kept (C1, C2, S4), are in `alchemy-devtools/AGENTS.md`; this file is about building, reading, changing and humanizing the source.

## Goal

The aim past DONE is the source itself, as clean, human and minimal as it can be made (Pascal, 12 November 2026). A change that adds a file, a wrapper, a table or a line has to leave the code plainer to read, or it does not go in.

- **DONE** is pret's 100%, never stricter: all six editions of a game build byte-identical from source, verifiable from `rom.sha1`; DONE code and data are both 100% (C2, in `alchemy-devtools/AGENTS.md`); no function is matched by an assembly body or inline asm beyond the proven `CAMELOT_ASM` helpers; nothing in the build reads a ROM, confirmed by an independent audit (O4); the C compiles with a current GCC (`make modern`); every fake match is tagged and counted (S2). Both games have reached it.
- **Finished** means more: every asset ported (A1), `recon/<game>` gone, no FAKEMATCH device left, a limited set of stock compilers (K1 to K3), every mechanism and scene humanized (H4), and each game linked from one linker script run through the C preprocessor, its editions told apart by the same `LANGUAGE` and patch-level tests as the C, as both games now are (Pascal, 9 November 2026).
- **Released** is where Alchemy turns from decompiling to a platform people build with: Finished, the ROM shiftable (a shift test passes), a playable build that skips the comparison with `BUGFIX` and `UBFIX` documented, both games built in CI from a clean clone without a ROM, the docs covering both games, and an independent leak audit (O4). It is a state of the source: no tag, no published release, and no licence file, as pret's games have none (Pascal, 12 November 2026). The matching method, counting and tooling then live in alchemy-devtools, which Alchemy neither installs nor runs, and this file is rewritten for people building with Alchemy (Pascal, 9 November 2026).
- **Humanized** means a reader learns how the game works from its source and from the docs written from it (H1). Humanizing ⚓️ is the work ahead.

## Where things are

- `games/<game>/src`, `include`, `sound`, `text`: each game owns its copy of what it uses. ☀️'s code sits in one folder per bank, grouped by the credits' divisions, with a scene's overlay one file; `games/tbs/src/README.md` maps the folders, and module headers follow the same paths under `include/module`.
- Each game links from one linker script, `games/<game>/ld_script.ld`, run through the C preprocessor with the edition defined as its C is: it lists every object of the main image in link order, and includes `games/<game>/src/system/overlay/overlay.ld`, one block per overlay, when the build defines `OVERLAY`; the build reads each image's objects from them into `objects.mk`, and the devtools read that list. An overlay's globals still written in assembly are ☀️'s `scene/bss/<name>.s` and ⚓️'s `<scene folder>/bss.s`. Neither game has a `recon/`.
- The `Makefile` builds everything; `tools/` holds its small C programs (`ags-*`); the optional Alchemy Devtools, cloned into the ignored `alchemy-devtools/` by `make devtools`, holds the Rust matching aids, the renderer and the progress count. `out/` and `tools/out/` are build output.

## Commands

Setup is in `INSTALL.md`; no edition needs a ROM to build. The reference ROMs the devtools read go under `roms/` as `tla-ja.gba` and so on, checked against `rom.sha1`, never committed.

```sh
make bootstrap         # the tools, the compilers, GAS 2.10 and libgcc (plain make does it too)
make compare-editions  # all twelve editions: required before every commit (W5)
make -j8 compare-tbs   # the six ☀️ editions; compare-tla-en for one edition
make modern            # both games' C with a current GCC: no errors (modern-tbs, modern-tla)
make test              # the build tools' tests
make devtools          # optional, Rust: clones alchemy-devtools the first time
git config core.hooksPath .hooks   # send verified measurements when pushing main
make progress          # DONE code and data (C2, in alchemy-devtools)
make land              # on main, before a landing (C3)
```

`make compare-editions` prints a lot: send it to a log file and count the `: OK` lines. After switching branches, delete `out/*/deps.mk` and `out/*/objects.mk`; after renaming sources, delete the editions' `out/` folders; after switching to a branch whose tools differ, `rm -rf tools/out/obj tools/out/ags-* && make tools`.

How to match, rank, adopt and run that work as agents, the toolkit's commands and what matching has measured about alchemy-gcc are in `alchemy-devtools/AGENTS.md`; read it before reshaping a change whose bytes moved.

## Boundaries

Ask Pascal first: any compiler, option, routing or alchemy-gcc change (K1 to K3); anything that changes what counts (C1 and C2, in `alchemy-devtools/AGENTS.md`; W6); deleting what cannot be restored; pushing or publishing outside the landing Workflow 4 authorizes.

Never bent: the legal rules (L1 to L3), the ROM kept out of the build (O1), and all twelve editions byte-identical (W5).

## Workflow

1. Work on a branch, in the main checkout unless another session shares it, then in a worktree of your own; `main` is the only long-lived branch.
2. Change the source so that every edition stays byte-identical (W5); a change that moves bytes is reshaped in source until it does not (O4), measured with `alchemy-devtools diff`.
3. Humanize one mechanism or scene at a time, each step byte-identical (H2).
4. Land with `make land` on the tree you push; Pascal authorizes syncing each verified batch to `origin/main` with its measurement (C3). Other pushes need his request.

## Rules

### Legal

- **L1** Never commit, upload or publish a ROM, private inputs or any copy of the game files. The cartridge logo lives only in `ags-header`, as in pret's gbafix.
- **L2** Evidence is our own ROMs, this repository and public documentation; never another project's Golden Sun work.
- **L3** Never use, open, read or mention leaked Nintendo or Camelot code or SDKs, or anything derived from them.

### Counting

- **C3** A landing carries its measurement: `make land` compares, tests, checks formatting, builds `make modern` and measures the tree you push; the pre-push hook uploads the reports; CI rebuilds all twelve editions from a clean clone without a ROM, checks a receipt against its own measurement, and starts the docs build. `.github/publication.md` describes publication and recovery.

### The oracle stays out of the build

The reference ROM judges the build and never feeds it. Reconstructing Camelot's compiler from habits across a whole game is allowed (K3); fitting a compiler, option or routing to particular functions is cheating.

- **O1** ROM bytes never reach the build, apart from the logo `ags-header` writes and the two exceptions A7 names. Nothing derived from the ROM steers the build or count.
- **O2** Every name is defined where its bytes are; layout is the linker script's order. No equate, alias or table gives a name an address, except Camelot's own fixed addresses (`FIXED_ADDRESS`), each listed once. An assembler equate holds only what its table computes or a value its evidence names; a size set only so the bytes come out right is a copied byte (S1); `.set` only switches assembly in or out.
- **O3** Scene, map and resource ids come only from their tables, used whole; overlay code never branches straight into the main image.
- **O4** A mismatch is fixed in source. Before a milestone, run an independent audit for leaks.
- **O5** Old git history, deleted files, backups and unreachable objects are never evidence.

### Humanizing

- **H1** A reader learns how the game works from its source; the bytes stay identical, nothing has to look like the original's source, and our names are never presented as recovered.
- **H2** Understand a thing before naming or explaining it. Take one mechanism or one scene at a time: find out what it is (callers, data, the game's text, the running game), then type it, name it, shape it and explain it in comments and its page. A name or comment written before the thing is understood is redone. Work that needs no understanding may run across the tree: formatting, moving files, a literal replaced by the name it already has, a comment the code itself proves. Other names and comments may not.
- **H3** Names come from evidence: the game's text, its area names (`gArea_NameRules`), or what the player sees at the moment the code needs (right room, flags, leader, camera). The code's own words are a guess, never a name. Code nothing reaches has no render to name it from: its name says what its code does, confirmed by staging it (Pascal, 5 November 2026). Game terms are the English release's. Where a game thing's `///` comment gives its evidence, it does so in one line: `★ Named from the game: "..." (MsgName)`, `★ Named from its area name: ...` or `★ Named from what the player sees: ... (its render)`. The count sees only that such a line is written: it is a claim that someone looked, made only after looking, and removed when found untrue.
- **H4** A unit is done when someone who has never seen it could follow it from its source and its page. That is judged by reading it, not by a list: start from what a reader cannot follow (a wall of bare numbers, a routine that says nothing of what the player sees), and no count that reads zero makes a unit done. What evidence could settle is settled; what it cannot stays a placeholder, or an open question as a `//` comment at the code: `XXX: <question>; <the evidence that would settle it>.` or `XXX (no evidence): <question>; <why nothing in reach settles it>.`, never on a page.
- **H5** `alchemy-devtools progress --humanity` is a worklist, not the definition; where a count asks for what these rules forbid, fix the count. A wrong name is fixed where it is; it becomes a rule only when it shows a principle these rules miss.
- **H6** ⚓️ is written as ☀️ expanded: where it keeps a routine, structure, mechanism, scene kind or habit ☀️ has, it takes ☀️'s names, words, layout and comments, changed only where its own code or evidence differs, and names afresh only what it adds (Pascal, 9 November 2026).

### Source

- **S1** `games/` holds only real source: C from an approved compiler, or proven assembly written as instructions, never copied bytes. Assembly is proven as the compiler library, as 8-byte far-call veneers, or as handwritten code with an instruction, frame or pattern alchemy-gcc cannot emit, its `@ Why` saying which: rrx; a branch, adc or sbc on a shift's carry; r11 as an ordinary register; a callee save without lr; CPSR/SPSR; swi; computed pc into code; stores into code; unpaired multiply halves; a pc-relative block load of data; a mode switch inside a function; movs with no shift; ldm or stm writing back off sp other than a block copy from r0 or a doubleword pair; a conditional branch on flags with no compare; one literal pool shared by two functions; a linkage no procedure-call standard produces; or a copy the ROM keeps of a routine it also links, whose bytes are that routine's but for what a link fills in (pool words left 0, a call outside its library to itself) and whose calls keep that routine's offsets, or which stops short of its end (Pascal, 8 November 2026). Anything else is written as C. No C file places bytes through `asm()`.
- **S2** A fake match is what pret marks as one ("needed to match", "fakematch"): a line or form that does nothing for the program, or misstates it, and is there only so the compiler emits the original's code. One test decides it, whatever the form's shape (revised 11 November 2026 at Pascal's request): write it the plain way; if the bytes stay the same, the plain way is the source; if they change, ask whether a programmer would have written this for the program's sake. If not, it is a fake match and carries one tag inside its function: `/* FAKEMATCH(<kind>): the form kept; as <plain form>, N of M instructions differ in tbs-en. */`, N measured by a whole-function `alchemy-devtools diff`. The kinds, ranked by how far each misleads a reader, a modern compiler or someone changing the game, worst first (the ranking is ours; pret has none): `signature` (a type that is false: a return, parameter, declaration or local typed other than what it holds, a `const` left off, a call through a function type the callee does not have); `pin` (a variable fixed to a register); `barrier` (an empty asm, or an asm operand or clobber that does not say what the asm does); `wrapper` (a call layer that exists only for the compiler); `volatile` (the qualifier on anything but hardware or memory an interrupt shares); `temporary` (a copy of a parameter, global or local, a pointer standing in for a local's own address, a local holding one constant or one pointer, or a local reused for a second value, where the plain expression compiles differently); `dead` (a store, read, test, arm or update that cannot change the result and for which the ROM keeps no instruction of its own: cancelling updates, self-assignments, never-true tests, both arms alike, a taken address, and a once-only block or loop, empty or round statements, that no macro expands to). Evidence (pokeemerald and pokefirered, finished; pokeruby and pmd-red, in progress; read 11 November 2026): the finished two have no register pin, no empty asm and no `NONMATCHING`, and mark as needed to match a parameter copied to a local, a pointer or unused local kept for the match, a variable reused, a self-assignment, `x *= 1`, an extern declared without its `const` and a header with a conflicting type; their only `volatile` locals are hardware's, their once-only blocks are macros', and their sixty-odd `goto`s carry no mark. So ☀️ takes no `signature`, `pin` or `barrier` (`make test` refuses the first two; the eleven barriers left are to go), and a device is added only in place of a worse one. Replacing a device with milder ones is progress, however many it takes. A device comes only after reshaping has failed. Never patch compiler output.
  A leftover is Camelot's own code that does nothing in this edition and still shapes its bytes: the original's, not ours, and counted apart from the fake matches (Pascal, 12 November 2026). One physical test separates the original's code from a device (Pascal, 12 November 2026). Code whose own instructions are in the ROM is the original's: where it cannot change the result (a test never true, a store nothing reads, a read whose value goes unused, a call whose result is dropped, both arms alike, a self-assignment the ROM keeps as an instruction), it is written as the ROM has it and marked `// DEAD:` (S3), and leaving it out is not its plain way. A form that leaves no instruction of its own in the ROM and only changes how other code compiles (cancelling updates that fold away, an empty once-only block or loop, a copy that changes register choice) is a device, and FAKEMATCH unless evidence shows it is the original's leftover. A leftover keeps its form and carries one tag inside its function in place of FAKEMATCH: `/* LEFTOVER(<kind>): what remains and its evidence; as <plain form>, N of M instructions differ in tbs-en. */`, N measured as for FAKEMATCH. The kinds: `frame` (storage the ROM's own frame reserves and no instruction addresses, such as an unused local or an idle element of an array) and `template` (a shape copied from sibling routines that use it, idle here: a second blitter, a loop over one target, deltas recomputed after a swap). The frame is evidence (Pascal, 12 November 2026): this compiler reserves stack only for what its source declares and for spills, and a spill slot is used, so stack the ROM reserves and never touches can only be storage the original declared. An unused local that only sizes the frame is therefore LEFTOVER(frame) at any size, its tag stating the bytes reserved (`sub sp, #N`) and the ones no instruction addresses, as the function's assembly shows them, and any stronger evidence there is (`games/tbs/src/debug/test.c`'s buffer, filled by a loop only the Japanese edition keeps); storage an instruction addresses is no leftover. Any other leftover names its evidence: another edition, or the same routine in ⚓️, uses the thing (reads it, gives it a second value, runs its loop), and the tag names that edition or routine; the same shape repeats down sibling routines that use it, named; or a macro or helper reconstructed as below explains the rest of its family. ⚓️ counts only where its twin uses the thing, never where it merely needs the same form: a device ⚓️'s ROM also needs is one compiler meeting one reconstruction twice, not Camelot's (Pascal, 12 November 2026), and a form ⚓️ carries because H6 writes it from ☀️ says nothing. A leftover claim without its evidence is a device and stays FAKEMATCH, and so is any asm statement. When in doubt, it is a fake match.
  A macro or inline helper reconstructed from a family of sites is ordinary C only when the same ghost appears at five or more sites of the same kind of place (two or three are a coincidence), one definition with the devices gone gives byte-identical code at every one of them in all six editions, its name says what its expansion does and never guesses the original's, and its `///` comment names the family and says the name is ours. A macro or helper below that bar, or one whose sites share nothing but the need to match, is a device in a costume and keeps its tag: wrapping a device removes no fake match. The count prints fake matches and leftovers on separate lines, each by kind, with the `// DEAD:` marks counted among the leftovers on a line of their own and never added to the fake matches; the fake matches are the number to drive to zero.
  Ordinary C, with no tag and only a short `//` note where the form would puzzle a reader: a default set where a local is declared or at the top of its function (`// Default:`; a whole routine has matched once its defaults were written in their order); `goto`; an equivalent spelling (`p[n]` or `*(p + n)`, `*&`, a cast that changes no type's meaning, a library routine called by name); an inline helper or a macro, with whatever its expansion holds, unless it stands where a device stood and falls below the family bar above; `volatile` on hardware; a local that holds a global or work pointer across calls (`struct BattleCamera *camera = gBattleCamera`) (12 November 2026); a local that names one constant and is initialised where it is declared (`s32 width = 48;`), as a programmer names a number for the program's sake, where one assigned later in the body stays a `temporary` (12 November 2026); a range test wider than the loop that feeds it, a designer's frame window and a loop's length being two numbers tuned apart (12 November 2026); a layer that explains a habit of the whole game (`event.h`, `iwram_call.h`, `system_call.h`); the original's own undefined behaviour, kept behind `UBFIX` with a `// UB:` note (S3). `CAMELOT_ASM("proof")` marks the proven handwritten helpers inside C. A tag with no kind is unfinished: it is given its kind, or removed with its form, when its function is next touched.
- **S3** Source is readable modern C in English, as pret writes its games:
  - Layout: lowercase short file names, the same folders in both games, code in its bank's folder, a function in the module of its linker neighbours. An object over about 3,000 lines holding several families may be written as parts in `<object>/` with a private `<object>_internal.h`, included in ROM order; a scene's overlay stays one file.
  - Language: C89 with the compilers' GNU extensions; types, signedness and scopes from the game's code; data read through structs and enums rather than offsets and casts wherever a match allows.
  - Naming: functions `Module_PascalCase`, globals `gName`, statics `sName`, constants and macros `UPPER_SNAKE_CASE` (a macro that stands for a call is named as a function, as the plain `Actor_SetPosition` over `Actor_SetPositionFixed` is), locals and fields `camelCase`; words spelled out except the abbreviations a programmer reads without stopping; an acronym is a word in mixed case and capitals in constants, as GBATEK writes them. `wait()` and `px()` are the lowercase primitives. The m4a driver keeps its own spellings. An unknown stays a placeholder (`sub_08012345`, `unk_14`).
  - Vocabulary: one name per concept, and each word in one sense, as `glossary.md` defines them. An event calls a command by its name in `event.h` (`Actor_FaceDirection`, `Event_ShowMessage`); the main-image routine's own name is written in a scene only where that site compiles differently through the inline. A word comes from, in order: the game's text (only for what the player sees), Camelot's own provenance (its labels, credits, staff interviews), the Sega lineage, the period tradition, plain English; never another decompilation's. The settled words are the glossary's; renaming one needs Pascal. Retired: tick, monitor, program (for a sequence), common, engine, library (for this code), job, main loop, kernel (for the main routine), task manager, metatile, text printer, scanline effect, sprite anim, round, battle animation, song (for every sound), record (in the save sense), interior (for a room), object (for an actor), and ⚓️'s place.
  - Numbers stay numbers until evidence gives them a meaning; then they have a name (an enum or macro in a shared header), and neither code nor comments use the number again. A number is decimal, or composed (`240 * 160`, `px(4) / 5` when exact, `TRIG_TURN / 8`, `DMA_COPY_WORDS(n)`, `RGB(r, g, b)`; a fraction of a pixel quantity, a position, speed, gravity or distance, is `px(n) / d`, and `Q16_ONE * n / d` is only for a unitless factor, a scale, decay, bounce or ratio); hex is kept only where the hex is the point: flag numbers (Camelot's debug flag editor shows them in hex), addresses, register values and bits, masks and packed fields, layout offsets, values from `0x80000000` up, all-ones markers and one-less bounds, raw stored bytes and the m4a driver's stock tables, and 16.16 values with no exact fraction (Pascal, 30 October 2026). A call or table row takes plain pixels and plain decimal speeds (`Actor_SetPosition(ACTOR_MIA, 880, 502)`, `Actor_SetSpeed(ACTOR_STATUE, 0.8)`), converted to 16.16 inside its definition by `Q16()`, which multiplies so that a negative is never shifted. A live 16.16 value goes through its `...Fixed` form (`Actor_SetPositionFixed`); a macro that reads each argument once may take live plain pixels (`Actor_SetPosition(actorId, x, z)`), and the macros that read one twice (`Actor_SetSpeed`, `FieldCamera_SetSpeed`, `FieldCamera_MoveTo`, `MapGrid_SetShake`, `ShipRooms_MoveCameraAndWait`) take only constants. `px()` turns whole pixels, a constant or a live value (`px(leader->x.part.pixel)`), into 16.16 only in arithmetic, comparisons and assignments on a stored 16.16 value (Pascal, 12 November 2026). Flags and sounds come from `flags.h` and `sounds.h`; a scene's temporary flag is named beside its includes.
  - Original behaviour: undefined behaviour keeps its form behind `UBFIX`; a bug keeps its code with `// BUG:` and a fix behind `BUGFIX`; `// DEAD:` marks code whose own instructions the ROM keeps and that cannot change the result (S2), and says what the ROM keeps: `// DEAD: <what>; the ROM keeps <its instructions>.` Unreachable things open their comment with `Unused:`; a function nothing refers to is `UNUSED`.
  - Editions: C and the linker scripts compare `edition.h` and `version.h` values; only plain assembly and `.S` files use edition names. `LANGUAGE` chooses only what language decides: text, message ids, fonts and glyph widths, and layout that fits the text. Every other difference between editions (a fix, a changed rule, value, check, timing or table) is a patch level from `version.h` (`TBS_PATCH_n`, `TLA_PATCH_n`), combined when no single level selects its editions (German alone is `PATCH_2 && !PATCH_3`) (Pascal, 7 November 2026). A value that differs by edition is one named macro chosen at the top of its file.
  - Macros: a macro that makes more than one call is a comma expression; wrapped in `do { } while (0)` it compiled differently in every ☀️ edition (10 November 2026).
  - Formatting: clang-format's LLVM style (`.clang-format`); include order is left alone; header guards are `ALCHEMY_<NAME>_H`.

### Documentation

The docs are the home page, the pages for what runs and what is shared, the folder READMEs, the glossary, the `///` comments and the site built from them (`alchemy-docs`). People read them; AGENTS.md is the only file written for agents. A unit's comments and page are written last, from what the earlier steps found.

- **D1** The docs are for a programmer opening this code for the first time, or one already in it looking for where something lives; nobody else reads them (Pascal, 12 November 2026). They explain how the game's systems work and how to think about them, a level above the code: not a modding manual, a wiki, a walkthrough or a how-to for changing the game, and nothing a comment in the source already says. A page gives the model of its subject, why it is built that way, and where its files are; field layouts, list sizes, row formats and which routine calls which are the source's to say.
- **D2** The docs are a tree that follows what runs, then the folders, each mechanism explained on exactly one page (D6) (Pascal, 12 November 2026). The home page (`games/tbs/README.md`) only orients: what is here, where to start, the map of the pages; it explains no mechanism. The main routine's page is the first chapter: one routine that runs four sequences in turn, each leaving in the main routine's work what runs next. Then a page for each sequence (the field, a battle, Lucky Dice, Lucky Wheels), a page for each thing every sequence shares (how code runs, which is waiting and tasks; windows and menus; sound; saving; game data; graphics; the Game Pak), and under those a detail page for one mechanism, which is its folder's README. A page has the sections its subject needs and no fixed set, and runs from a few hundred words to about a thousand. Each is written to a brief, kept out of the page, of what a reader should come away knowing, taken from the questions people arrive with (how is a new piece of state saved; what formats, colours and sizes can a picture have), and is judged by whether it answers them. A diagram shows the shape of the logic and nothing else: a box that needs a number, a field name or a condition to make sense belongs in the code, and a straight chain of boxes that only repeats one sentence is not a diagram; a reader who looked only at the diagrams, page by page, should come away with the right picture of the game. A section about something the player sees opens with its recording (D4). A table only where the values are the lesson, never a list of functions, files or an enum's numbers; one example where it makes a model click, never a walkthrough that teaches several mechanisms on the way through. The pages are rewritten to this shape from the home page down, one at a time; a page whose turn has not come keeps the form it has, and what it holds that no comment says moves into the source's comments before it is cut.
- **D3** Every place, person and event a page names is checked against the game's text and data and named as H3 names it; an internal number never stands in for a name.
- **D4** Pictures are the game itself: recordings and screenshots from `alchemy-devtools render` on a tbs-en build, published to the Blob store and referenced by their `https://alchemy.pascalpixel.com/` URL, with no text baked in. A recording is looked at before it is used: it must show what its name and caption say, and the checks that pass one prove only that pixels changed. Code the game never reaches is shown only staged by hand (`render guide --only unused`, one row a function), captioned as staged, never as how it "would play"; without a stage it has no recording (Pascal, 5 November 2026). A section about memory or timing has no recording. One that passes through a black screen shows at least ten seconds of the game before, between and after each (`render check` refuses otherwise). Small Mermaid diagrams, in the colours the docs already use and with the concept emoji (🏡 the field, ⚔️ a battle, 🎲 Lucky Dice, 🎰 Lucky Wheels, 🚩 a flag, 🎵 music, 📣 a sound effect), show a structure or order no recording can. Never a hand-drawn picture or a data dump.
- **D5** The docs are written by someone who loves this game, for a reader who does too (Pascal, 11 November 2026; `games/README.md` is his own and sets the voice). A page may greet the reader, say why a thing is worth their time and enjoy itself. Plain English a programmer who has never seen this code can follow, in short paragraphs of one thought each. Open on what the reader can see or do, and name the term after; give the reason right after the definition; choose one vivid example from the game over an inventory; say a claim once, in its plainest sentence; let a short sentence carry the news. A page that reads like a specification is redone. A programmer's own words (a loop, a pointer, a struct, a pixel, fixed point) need no explaining; the game's and the console's (a task, a sequence, an overlay, VBlank) are explained once, where they are first needed, or linked to the glossary. A page names a function or a file only where the reader will go and read it; which function calls which belongs to the source's comments. Enthusiasm is for the game and its engineering, and every fact stays exact. No retelling of the plot, and nothing about how the decompilation was made (a spelling kept for the compiler, the build's checks) beyond the introduction; `you` is the reader, the player is the player; headings name their subject or ask the reader's question.
- **D6** Say a thing once. Every mechanism, value, diagram and recording has one owning page, and every other page links there; a recording alone may open a section on each page that has one about it. What the project is, only in `games/README.md`; a sentence every site would repeat, once at the layer it describes. Before landing a docs batch, count the phrases, tables, diagrams and recordings it repeats across pages.
- **D7** A folder's README is its page; its `#` heading is unique. Link a glossary word at its first use, once. Where a word comes from is said only in the glossary's `Evidence:` lines and a folder's `## Evidence`, never in prose. Prose names the games, never ☀️ or ⚓️, and cites no rule of this file. A heading other pages link to is renamed only with those links. The site's settings live in `alchemy-docs`, never as markup in the source.
- **D8** A number is said by the name the code gives it and in the player's units; a number with no name gets one in the code first. Hex only as data a reader meets, in code formatting, as every symbol is. A cell behavior is said by what it does, never by its number.
- **D9** Comments say what the code cannot: what the player sees, units, why a forced form is forced, the evidence for a name. A comment the name or body already says is deleted. Declarations take `///` (a trailing `///<`), everything else `//`; a file opens with `/// @file`; no `@brief`; `@param` only where a parameter needs saying; the first sentence is the summary. FAKEMATCH tags, `// BUG:`, `// DEAD:` and comments inside functions stay `//`. An event's message call has the line it shows above it, quoted from the English text (`// "Is Jenna back yet?"`, a question with its `Yes:` and `No:` answers), wherever the event's message number is certain at that call; a quote is never guessed.

### Assets

- **A1** The build is as plain as pret's: C, assembly, indexed PNGs with real palettes, WAV, MIDI, PO text, one `map.txt` per map, and TSV only for a table an encoder packs; never raw dumps, blobs or stored compression tokens (A7 excepted). Each asset builds beside its source, ignored by git.
- **A2** A picture is drawn the way the game shows it: sheets at their real width or sprite shape, tilemapped pictures as the map shows them, animations one frame wide.
- **A3** An all-grey palette only where the build writes that palette from it.
- **A4** Every file an encoder reads is a prerequisite: one Makefile rule per kind of asset, with the encoder listing what else it read in a `.d` file beside its output.
- **A5** No JSON, apart from `.recomp.json` and `.recomp-2.json` at the root, one per game, which recomp.fyi reads and nothing here does (Pascal, 5 November 2026). A table the code reads as it stands is a C array at its place in the ROM, read through its struct with designated initializers and a comment naming each entry from the game's text.
- **A6** Each edition combines its text, fonts and layout with its measured code differences; differing resources are chosen in their owning module or rule.
- **A7** Two kinds of bytes are known only by comparing with the ROM, and are kept as named, counted exceptions, the data's fake matches (the independent audit of 11 November 2026 raised them; Pascal left the ruling to the agents). A packing patch (`*_patch.tsv`: 13 files, 158 positions in both games) has the packer read one byte where the asset ships another, because the shipped asset differs from the one Camelot's packer saw; each line gives its proof, and the plain form is the asset packed with no patch. Residue (`PACKER` lines in each game's `overlays.s`: 406 in ☀️, 537 in ⚓️) is what Camelot's writer left after a packed overlay, which no program reads. pret commits whole binary files where data will not reproduce, so this is no stricter than pret (W3). Neither grows: a new one needs Pascal. A playable build may drop both, and an audit counts them.

### Compilers

The set is frozen: three C generators built from the pinned `alchemy-gcc` submodule (GNU's GCC snapshot of 2000-07-31, GNU's GCC 2.95.2 and pret's `old_agbcc`) with the parts the build never reads removed and host fixes that let them build and run on a current Mac and change no output. The snapshot also carries one code-generation change, `-mtune=gba` (K2); the rest is stock (Pascal, 8 November 2026). No new compiler, option, route or alchemy-gcc commit, except a host fix. Matching shows practical compatibility, not Camelot's exact compiler.

- **K1** Game Thumb C: alchemy-gcc (GCC of 2000-07-31) with `-O2 -mthumb -nostdinc -fcall-used-r4`, plus `-mthumb-interwork` for ☀️ and `-mtune=gba` for ⚓️ (K2). ⚓️'s C linked only into overlays takes `-Os` in place of `-O2`, a route by whole file and place in the build, never by function; its main image stays at `-O2`. libgcc with `-O2 -mthumb -mcpu=arm7tdmi -fno-inline`. ARM C: GCC 2.95.2 with `-O2 -mthumb-interwork -fomit-frame-pointer -fcall-used-r4`. Sound and flash: pret's `old_agbcc`. The Makefile's SOUND_C, FLASH_C and ARM_C are the only routes. What ☀️ routes through them, ⚓️ may route the same way, by whole file and by what the code is: ARM instructions, or the sound and flash libraries (Pascal, 5 November 2026).
- **K2** ⚓️ takes ☀️'s options without interworking, plus `-mtune=gba`. Options and tune are chosen by what the ROM and the hardware show, never by how much they match (Pascal, 8 November 2026): ⚓️'s 6,725 `pop {pc}` returns rule out interworking, which ☀️'s code never returns with. `-mtune=gba` is the ARM7TDMI tuned from GBATEK alone, as one engineer could have done it in a weekend in 2001: loads timed `3 2` (LDR 1S+1N+1I), stores `3 2` as loads, multiplies `3 3` (MUL 1S+mI, m = 2, an operand within 16 bits); without interworking, a call through a register is GBATEK's `mov lr, rN` and lone `bl` suffix instead of the `_call_via_rN` veneer; and a constant is built in its register instead of read from cartridge ROM, 255 below it first, else its low byte above a shifted byte. The 255-first order is read from the ROM: of its 13,828 split constants, the 4,017 where the two orders differ all take 255. The constant is built once, by the split pass after reload, and a constant move that first appears after it is left to the literal pool as stock GCC leaves it (Pascal, 11 November 2026). The ROM shows it at one site and nowhere against it: `Text_DrawPrefixedNumberAtOffset` stores the HP label's second tile in both branches in Japanese, English and German; `reload_cse_move2add` makes each `r3 += 1` and `r3 -= 1`, and cross-jumping, after the second scheduling pass, rewrites both as one load of `0xf01e` and merges them, which the ROM reads from its pool 90 bytes away where the two constants before it in the same function are built; of 35 other constants loaded after a join every one existed before the split and is built, and no other plain integer the tune builds is pooled at a word load's reach. With it that routine is one source in all six editions, ☀️'s too, and no other unit of either game compiles differently (about 4,490 units an edition, at `-O2` and `-Os`). Building constants at two moments, as alchemy-gcc did until then, was our doing; building them at one is the plainer engineering, and probably what a weekend's change would be: the tune as a whole is thin beside what GBATEK's timings would support, and is kept as Camelot's, not improved. Evidence (tla-en, 8 November 2026): against the C matched before, the tune differs in 805 functions where stock ARM7 tuning differs in 4,265; ☀️ under it differs in 3,314 of 7,715, so ☀️'s compiler had none of it. GBATEK's STR, 2N, alone gives stores `2 2`; `3 2` is read from the ROM by replaying 568 functions both games share by name and size, ☀️'s C compiled with ⚓️'s options and compared in shape with ⚓️'s ROM: `3 2` beats `2 2`, `2 1`, `3 1`, `3 3` and `4 2`, 245 twins exact against 236, and against `2 2` brings 53 closer and 8 further (8 November 2026). The twins cannot separate multiply timings (shared code has few multiplies); `3 3` is Pascal's reading of GBATEK (8 November 2026). An instruction-order mismatch alone is no reason to change compilers.
- **K3** A code-generation change needs evidence from the hardware or the ROM itself, never from how much C it matches; it lands in alchemy-gcc as its own commit with that evidence, recorded here, and with Pascal's approval. An option change needs one option set that explains most of a game's code, its evidence recorded here, and Pascal's approval.

### Work

- **W1** A plain Makefile whose every rule can be read; a build tool is a small tested C program; Rust only in `alchemy-devtools`; no TypeScript, JavaScript, Python or shell beyond a command line; tooling nothing needs is removed.
- **W3** Follow pret where it settles a question, and never be stricter.
- **W5** Before every commit, `make compare-editions` prints OK for all twelve editions. Builds are incremental, as pret's are; CI builds every push from a clean clone.
- **W6** A change to what counts (C1, C2), a rule, an option or routing lands as its own commit with DONE before and after.
- **W7** Parallel work divides by owner; check a name is free (`git log --all -S`) before using it; commit only verified work.

### Nothing but the source

The repository is a few short C files, pictures, music and tiny tools, as pret's are; caches, registries and scaffolding that make it look bigger than it is drift from the code.

- **N1** A tracked file under `games/` is read by the build or is a guide's Markdown.
- **N2** No caches: what a script can produce from the source is produced by the build or the docs site, never committed.
- **N3** No registries kept by hand: a fact lives once, beside the thing it is about.
- **N4** No per-asset recipe files, stored offsets or sizes; one rule per kind of asset.
- **N5** No background files: notes and plans stay in the agent's scratch space.
- **N6** Volume is never progress: add no file, table, section or line to look thorough; every new file says what reads it.
