# coverage-map

A native Rust tool that derives the ROM coverage map for a decomp target from
the live source tree and tracked evidence files. The former
`tools/metrics/coverage_map.ts` implementation is retained below only as
historical migration evidence.

## State: the port is complete

The migration parity run reproduced every flag and output byte-for-byte against
the former implementation.

| flag | status |
| --- | --- |
| *(default)*, `--target`, `--exact-ref`, `--semantic-ref`, `--help` | ported, byte-exact |
| `--check` | ported, byte-exact stdout and exit status |
| `--write` | ported, all six tracked artifacts byte-identical |
| `--self-test` | ported, runs the same assertions at runtime |

What landed in this pass: the squarified treemap (Bruls/Huizing/van Wijk), the
1200x660 dashboard SVG renderer, the 540x304 SpaceMonger box-tree renderer with
its embedded base64 OTF font, `verified_asset_tiles`, `asset_families_by_source`,
`asset_maturity_tiles`, a hand-written SHA-1 (FIPS 180-4) behind
`svg_cache_version`, RFC 4648 base64, `readme_with_cache_buster`,
`readme_with_done_headline`, and `self_test`.

The former TypeScript renderer and dashboard sidecar are retired. The native
binary is now the production implementation and is invoked through `make coverage`
and `make coverage-check`.

## Closure: fully native

The native implementation uses the shared coverage, JSON, and target-resolution
logic directly. It has no sidecar and shells out to nothing at runtime. The
former migration parity harness described below was used only during the
migration and is not part of the production path.

The three shared modules are pulled in with `#[path]` from
`tools/full-c-progress/src/`, which is a bin-only crate and therefore not
linkable as a dependency.

## Historical reference-implementation bugs, reproduced rather than fixed

Each has a `PORT NOTE` at the site.

1. `retainedMainSpans()` builds the full-build manifest path with an extra
   `".."` after three `dirname` calls, resolving outside the repository root.
   The manifest is therefore never found and the function always falls back to
   `semantic/main-regions.json` alone.
2. `semanticSpans` parses `semantic/regions.json` twice.
3. `svgPath(target)` is defined and never called.
4. Contract drift: `manifestRanges`' `sourcesOf` matches extensions with
   `/\.[a-z0-9]{2,5}$/i` while `assetMaturityTiles`' `gatherSources` uses
   `{2,4}`, so a five-character extension such as `.4bpp` is seen by one and not
   the other. Both spellings preserved verbatim.
5. `--help` calls `process.exit(0)` *inside* the argument loop, so a bad flag
   after `--help` is never reported.
6. The `--check` semantic guard reads the *resolved tree*'s id, not the
   document's recorded provenance. When no semantic tree resolves, the id is
   `undefined` and never equals any tracked string — not even the literal
   `"none"` the document records — so an unresolved run can never report the
   rendered map stale.

Repository state, not a port bug: `metrics/gs1-en-coverage-map.json` is stale
against the current worktree (exact +724, semantic −1,388, executable +30), so
`--check` reports it stale from both mirrors, byte-identically. Deliberately not
regenerated.

## JS-semantics traps that actually bit

- `Number.parseInt(text, 16)` accepts a leading `0x` and consumes the longest
  valid prefix. A strict whole-string hex parse silently returned 0 for all 329
  addresses in `asm/alignment.json` (over-crediting exact main coverage by 526
  bytes) and for all 16 addresses in `semantic/main-regions.json` (moving 980
  bytes from `retained_asm` into `assembly`). Every numeric parse in the crate
  and in the three `#[path]`-included shared modules now goes through the
  `jsnum` helpers, which strip `0x`/`0X` first; no bare `from_str_radix` or
  `parse::<>` reaches input text.
- Object spread rewriting an existing key keeps that key's original position;
  `trackedDocument` depends on it.
- `NaN` comparisons: `Infinity - Infinity` is `NaN`, JS `||` treats it as falsy,
  and a comparator falls through to its tiebreak. The treemap's aspect-ratio
  comparison divides, so a zero-area row reaches exactly this. Named helpers
  (`js_greater`, `js_less`, `js_not_equal`, `js_greater_than_zero`) keep the
  raw float comparison rather than routing through `partial_cmp`/`total_cmp`,
  which both get it wrong. Nothing is `#[allow]`-suppressed.
- `localeCompare` is ICU collation, approximated here by UTF-16 code-unit order
  (`jsnum::utf16_cmp`). The parity run does not distinguish the two on the real
  inputs — no divergence appeared — but that is evidence, not proof.
- No `HashMap`/`HashSet` anywhere: JS `Map`/`Set`/object iteration order is
  insertion order and load-bearing, treemap placement order is output-visible,
  and `Set` silently dedupes.

## Layout

`lib.rs` plus a thin `main.rs`; modules for the pipeline, assets, tree
resolution, treemap layout, the two renderers, SHA-1/base64, `jsnum`, the CLI,
and `selftest.rs` (a runtime path, not `#[cfg(test)]`, because the native CLI
exposes it as `--self-test`).

`cargo test`: 115 passed, 0 failed. `cargo clippy --all-targets -- -D warnings`:
clean, nothing suppressed.

Test fixtures are assembled under `target/fixtures/`, which is untracked and
inside the one directory this crate owns.
