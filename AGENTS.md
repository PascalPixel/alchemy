# Alchemy

It instructs the agents that work on Alchemy; people read `README.md` and `INSTALL.md`. The agents keep it current, wording included. Pascal decides compilers, what counts as DONE, and deleting anything that cannot be restored; everything else goes ahead without asking, including fixing a check that wrongly blocks honest work as long as it still refuses everything it refused before.

Alchemy rebuilds Golden Sun: **The Broken Seal** (☀️, build `tbs`) and **The Lost Age** (⚓️, `tla`) byte for byte from readable C, assembly and editable assets, in Japanese, English, German, Spanish, French and Italian: twelve editions, `tbs-ja` to `tla-it`. Japanese releases are the source editions; localizations are measured differences.

## Goal

- **DONE** is a pair, counted over all six editions of a game (C2): code (matching C and proven assembly) and data (bytes placed from source). **100%** is pret's standard, never stricter: all six editions build byte-identical from source and anyone can verify them from `rom.sha1`; DONE code and data are both 100%; no function is matched by an assembly body or inline asm beyond the proven `CAMELOT_ASM` helpers; nothing in the build reads a ROM, confirmed by an independent audit (O4); the C compiles with a current GCC (`make modern`); every steering device is tagged and counted. ☀️ has reached it; ⚓️ is still being matched.
- **Finished** means more: every asset ported (A1), `recon/<game>` gone, no FAKEMATCH device left, a limited set of stock compilers (K1 to K3), and the code humanized (S3). Humanizing runs in byte-identical passes: mechanical (formatting, dead code, prototypes, type warnings, stale devices; undefined behaviour keeps its form with the defined one behind `UBFIX`; original bugs keep their code with pret's `// BUG:` and a fix behind `BUGFIX`; unused functions are `UNUSED`), then structure (files grouped as the original's objects, repeated code folded into the game's own helpers and macros), then meaning (English names from evidence).
- PostgreSQL at `~/Developer/postgres/postgres` is the humanization quality reference: comments explain purpose, invariants and ownership, proven numbers have names, and formatting is consistent. Alchemy keeps S3's C89, naming, documentation and formatting conventions; `games/tbs/src/effect` shows its local forms.

## Where things are

- Source: `games/<game>/src`, `include`, `sound` and `text`; each game owns its copy of what it uses (its engine headers in `include/<folder>`, ⚓️'s copies of ☀️-numbered assets under ⚓️'s own numbers), and sharing may be revisited when both games are complete. ☀️'s code sits in one folder per bank of the main image (`runtime`, `field`, `window`, `game`, `menu`, `shop`, `battle`, `effect`, `object`) beside `graphics`, `map`, `sound`, `system`, `debug` and `scene` (each scene overlay is `scene/<place>.c` with `scene/entry/` and `scene/import/` tables). Unit headers follow the same paths under `include/unit`.
- `games/<game>/objects.tsv` lists every object in link order with its sections and editions; `games/<game>/main.ld` is the one main script, chosen by `--defsym <GAME>_EDITION_<LANG>=1`. ☀️'s overlays link through `games/tbs/src/system/overlay/overlay.ld`; ⚓️'s are one script each under `recon/tla/raw/overlays`.
- `recon/tla` holds ⚓️'s not-yet-C work: `raw/` listings, `<lang>/` scaffolds, `en/main/<address>.c` drafts. ☀️ has no `recon/`.
- `games/tbs/src/effect/effect.c` is one object written as parts: it includes `effect_internal.h`, the private header every part also includes, then the files under `effect/parts/` in ROM order (S3).
- The `Makefile` builds everything; `tools/` holds the small C programs it runs (`ags-*`); the optional `alchemy-devtools` submodule holds the Rust matching aids and the progress count. `out/` and `tools/out/` are build output.

## Commands

Setup is in `INSTALL.md`; ROMs go under `roms/` as `tla-ja.gba` and so on, checked against `rom.sha1`, never committed.

```sh
git submodule update --init --recursive alchemy-gcc
make bootstrap         # the tools, the pinned compilers, GAS 2.10 and libgcc
make compare-editions  # all twelve editions: required before every commit (W5)
make -j8 compare-tbs   # the six ☀️ editions; compare-tla-en for one edition
make modern            # ☀️'s C with a current GCC: no errors
make test              # the build tools' tests
git submodule update --init alchemy-devtools && make devtools  # optional, Rust
git config core.hooksPath .hooks   # send verified measurements when pushing main
make progress          # DONE code and data (C2)
make land              # on main, before a landing (W2, C3)
alchemy-devtools/target/release/alchemy-devtools diff DRAFT.c [ADDR] [--show|--heat|--rtl]
alchemy-devtools/target/release/alchemy-devtools permute DRAFT.c [ADDR] [--minutes N]
```

`make compare-editions` prints a lot: send it to a log file and count the `: OK` lines.

## Boundaries

Always: keep all twelve editions byte-identical (W5, W8); tag every compiler-steering device with its measured difference (S2); name only from evidence (S3); commit each verified step, attempts included (S4, W7); look at how pret does it first (W3).

Ask Pascal first: any compiler, option, routing or alchemy-gcc change (K1 to K3); anything that changes what counts (C2, W6); deleting what cannot be restored; pushing, pulling, fetching or publishing outside the verified humanization sync authorized in Workflow 6.

Never: commit or publish a ROM or game files (L1); use another project's Golden Sun work (L2), or leaked Nintendo or Camelot code or SDKs or anything derived from them (L3); let the ROM steer the build or count (O1); write a function as inline assembly, patch compiler output or give a function its own compiler option (S2, K1); treat old history or deleted files as evidence (O5); add JSON, Python, shell or TypeScript programs (A5, W1).

## Workflow

1. Work in the main checkout on a branch; `main` is the only long-lived branch, and Pascal prefers no worktrees (W2).
2. Match what other unfinished code calls first, then the largest with nothing left to name (W4).
3. Draft in `recon/<game>/en/main/<address>.c`; a near miss stays a draft with its remaining difference in its header (S4).
4. Adopt a match into the module of its linker neighbours, in every edition whose bytes agree, and commit (C1, S4).
5. Humanize in passes, each byte-identical (Goal).
6. Land with `make land`; Pascal authorizes syncing each verified humanization batch on local `main` to `origin/main`, including its progress measurement (W2, C3). Other pushes need his request.

## Rules

### Legal

- **L1** Never commit, upload or publish a ROM, private inputs or any copy of the game files. The cartridge logo lives only in the header fix-up tool, `ags-header`, as in pret's gbafix.
- **L2** Evidence is our own ROMs, this repository and public documentation. Never use or open another project's Golden Sun work.
- **L3** Never use leaked Nintendo or Camelot code or SDKs, and never open, read or mention sources that might contain them, nor anything derived from them.

### Counting

- **C1** A function counts only when its whole extent, literal pool included, compiles exactly and every edition stays byte-identical, and in an edition only when that edition links its C. _Check: make compare-editions._
- **C2** DONE is pret's calcrom over the linker maps, by folder: bytes placed from `games/` are done, from `recon/` not yet. Each image counts from its first to its last placed byte (overlays once, unpacked). Code is `.text` (C, assembly, 8-byte stubs and the compiler library reported apart); data is everything else. A game's figure sums its six editions; 100% needs both at 100% in all six.
- **C3** Every push to main carries its measurement: stage all source changes, then `make land` compares, tests and measures the same tree; the pre-push hook uploads immutable reports and their timestamped receipt to `decomp-reports`. `make land` also runs the tool tests, the format check and `make modern`; CI then proves only what anyone can check without our machines: the six ☀️ editions rebuild from a clean clone with no ROM. After that build passes, CI validates the receipt, archives the figures, accepts the measurement and starts the `alchemy-docs` site build on Vercel through a deploy hook; that site serves the docs and README's figures. The old `progress` branch is a frozen archive, never updated. `.github/publication.md` describes publication and recovery.

### The oracle stays out of the build

The reference ROM judges the build and never feeds it. Reconstructing Camelot's compiler from habits across a whole game is allowed (K3); fitting a compiler, option or routing to particular functions is cheating.

- **O1** ROM bytes reach the build only through pret's `.incbin "baserom.gba"` scaffold in `recon/`, which never counts, and the logo `ags-header` writes. Nothing else derived from the ROM or expected output steers the build or count; `out/` reports are for people only.
- **O2** Every name is defined where its bytes are; layout is the object list order. No equate, alias, `#define` or table gives a name an address, except Camelot's own fixed addresses (resident IWRAM routines, RAM buffers addressed as constants, the cartridge restart entry), each listed once and checked against the link. One name per place.
- **O3** Scene and resource ids come only from their tables, used whole. Overlay code never branches straight into the main image.
- **O4** A mismatch is fixed in source, or the code stays a draft. Before a milestone, run an independent audit for leaks.
- **O5** Old git history, deleted files, backups and unreachable objects are never evidence.

### Source

- **S1** `games/` holds only real source: C from an approved compiler, or proven assembly written as instructions, never copied bytes. Assembly is proven as the compiler library, as whole 8-byte far-call stubs, or as handwritten, which it is only with an instruction, frame or pattern alchemy-gcc cannot emit (rrx; a branch, adc or sbc on a shift's carry; r11 as an ordinary register; a callee save without lr; CPSR/SPSR; swi; computed pc into code; stores into code; unpaired multiply halves; a pc-relative block load of data; a mode switch inside a function; movs with no shift; ldm or stm writing back off sp other than a block copy from r0 or a doubleword pair; a conditional branch on flags with no compare; one literal pool shared by two functions) or a linkage no procedure-call standard produces. Anything else stays in `recon/` until it matches as C.
- **S2** Compiler-steering devices, by kind (`wrapper`, `volatile`, `temporary` for a forced temporary, `dead` for dead code, `one-pass` for a once-only block or loop, `barrier` for an empty asm, `pin` for a fixed-register variable), count, as in pret, when each carries a tag inside its function in one form, `/* FAKEMATCH(<kind>): the form kept; as <plain form>, N of M instructions differ in tbs-en. */`, where the kind is one of the devices listed here and N comes from a whole-function `alchemy-devtools diff` (or the function's instructions in its object's assembly) against the edition named; dates and attempts go in commit messages; removing them is humanizing. In ☀️ their counts, and the count of `goto`, may only fall; ⚓️, whose compiler is not yet right, may add tagged devices to reach a match (Pascal); trading one device for another is no progress unless the new form is the source's. A device is for instruction order, register choice, a frame gap one unused local of a real type explains, or a form the bytes prove the source had; it comes only after reshaping has failed, and a function is never inline assembly. A `goto` is plain C and untagged, but one that only forces a layout goes when its loop is found. `CAMELOT_ASM("proof")` marks the proven handwritten helpers inside C: `Dma_Set`, `Transform_SetIdentity`, `Iwram_Call2`, `WaitFrames`' stack switch, `MulQ16`, and the `swi 2` and `swi 3` BIOS calls. A layer that explains a habit of the whole game is source, not a device: the ☀️ scene script layer (`field_event.h`, `field_service.h`), the IWRAM call layer (`iwram_call.h`) and the engine call layer (`engine_call.h`). A statement macro takes the shape its sites match with: `do { } while (0)` is no device where every use matches through it, but it compiles as a one-pass block in alchemy-gcc, so comma expressions and plain `{ }` blocks are often what match; a device inside a macro counts at each use. Never patch compiler output.
- **S3** Humanize: readable modern C in English, as pret writes its games. The bytes stay identical; nothing has to look like the original's source.
  - Layout: lowercase, short file names, the same folders in both games; `NAME.S` is assembly the C preprocessor reads, `name.s` plain assembly. Rename a file with its includes and object list rows. Each game keeps its own copy of code both use; a function goes into the module of its linker neighbours. An object the ROM shows as one may be written in parts: one `.c` file that includes them at its end in ROM order, each part one family or run, opening with what it holds, then a plain `// Part of <object>.c.` line; the parts are ours, not Camelot's files.
  - Language: C89 with the GNU extensions the compilers accept, `//` comments included; prototypes, `typedef`, `enum`, structs; types, signedness and scopes from the program and the matching evidence.
  - Naming, as pret's: functions `PascalCase`, globals `gName`, file statics `sName`, constants and macros `UPPER_SNAKE_CASE`, locals and fields `camelCase`; game terms take the English release's names. Places are named as the game names them: each scene by its area name in `gScene_AreaNameRules` (`object/scene_rules.s`, read through `Scene_GetAreaNameIndex`, an offset from `MsgDebugEntryName` in `text/en.po`), and a character by the name the game's text gives, introduced as the game introduces them; a name drawn from the code's own mechanics for a place, a room or a person (a "raised warehouse approach", "pillar rooms") is never written. Where the game gives a room no name of its own, the room is named, and its comment written, by what the player sees there and what sets it apart (CrossboneIsleFloodgate, for the floodgate the player closes to float its logs), checked against its render and recordings before it is written: what the code calls a thing (a "pillar") is not what it is (a log). As the game writes them: Psynergy is uncountable ("uses Psynergy", never "a Psynergy" except before another noun, as in "a Psynergy Stone"); one Djinni, several Djinn. What Move pushes is a stone pillar ("It's just a stone pillar."), or an ice pillar where Frost makes one, never a block; a block is a map's 16-pixel picture or a block of memory. A name says what the thing does; an unknown stays a placeholder (`sub_08012345`, `unk_14`). The ROM keeps no names: ours are never presented as recovered. A name of a place, person or thing carries its evidence in one line of its `///` comment, in one of three forms a tool checks: `Named from the game: "It's just a stone pillar." (MsgFieldJustStonePillar)`, `Named from its area name: Bilibin Barricade`, or `Named from what the player sees: the floodgate the party closes to float its logs (its render)`; a game-thing name without that line is unchecked, and `alchemy-devtools progress --humanity` counts and lists them. Names of code mechanisms need no line: the code is their evidence.
  - Comments: English, short, saying what the code cannot (what the player sees, units, why a forced form is forced, the evidence for a name). FAKEMATCH tags say what they steer.
    - A comment a reader could rebuild from the name, signature or body is deleted, not reworded; a comment on a statement explains a condition, order or constant the code does not show.
    - A sentence that would be identical at many sites is said once, at the layer or macro it describes, and each site keeps a short tag pointing to it; a FAKEMATCH tag is at most three lines.
    - A function or event the game can never reach (a scene no cell or table leads to, a branch its flags rule out) opens its comment with `Unused:` and then says why, and what the player would have seen; the docs head it "(unused)". Where it holds something the player would have seen (an event, a scene, its scripts and tables), its name carries `Unused` right after its family prefix (`Event_UnusedGaretJoinsIsaac`, a table `gScene_Unused...`), so the code says it as plainly as the docs; a helper nothing calls keeps its name, since `UNUSED` already says it. A function nothing refers to at all is `UNUSED` as well. What only the debug menus reach is not unused: its comment says the debug menus reach it, and its name stays.
    - A function's comment says, where the code shows it, who reaches it and what state it changes; when the reason for an unusual form is known the comment says why, and when it is not, `XXX:` says so and what evidence would settle it. A hedge is only `XXX: likely X, because Y`.
    - A field gets a `///<` note as soon as anything about it is known, placeholders included; packed bits get a one-line bit layout (`/// bits: 7 battle | 6 field | 3..0 kind`).
    - A summary over about 15 lines that describes a family belongs in the folder README; the code keeps a pointer.
  - Documentation comments, in Doxygen's line form: a comment that documents a declaration (a file, function, global, type, struct, enum, macro or field) is `///`; every other comment stays `//`.
    - The text is the same plain English. No `@brief`: Doxygen takes the first sentence. No `@param` or `@return` unless a parameter needs saying; then `@param name` with the sentence that already said it.
    - The first sentence is the summary: it ends before any quoted game text, and holds no abbreviation with a full stop ("e.g.", "Mt."). Message blanks go in backticks (`` `<unit> takes <damage> damage!` ``).
    - A file's opening comment is `/// @file` with its summary on the `///` lines after it; a file with none gets none invented. A part's `@file` says what it holds; the plain `// Part of <object>.c.` line after it names its object, and the folder README says once how parts are compiled. A stock sentence every file would repeat never goes in a `///` comment, since the docs site shows each one.
    - A trailing note on any declaration (a field, enumerator, table column, macro or global) is `///<`, its continuation lines too.
    - FAKEMATCH tags, `// BUG:`, `// DEAD:` and comments inside function bodies stay as they are: they describe matching, not the interface. So do a block a blank line separates from what follows, a section heading or label over a run of declarations, a comment above `#if` or `#include`, and `// clang-format off` and `on`, which clang-format reads only in that form.
    - Everything the docs site shows follows the Documentation rules, D1 to D7.
  - Formatting: clang-format's LLVM style, as `.clang-format` records it; include order is left alone, since it decides which declarations are in scope.
  - Numbers stay numbers until evidence gives them a meaning; a constant never invents an address or table id. Once a value has a meaning it has a name, and neither code nor comments use its number again: a scene is its `SceneId_` (`SceneId_UnusedMercuryLighthouseAerie2`, never "scene 59"), an element its `ELEMENT_` name or "the four elements" (never "element 0 to 3"), a door its `scene_links.h` name, a mode, state, kind, slot, variant or cell code its enumerator, and a `switch` on such a value switches on those enumerators. A value with a meaning and no name yet gets an enum before the comment about it is written. A number appears only as data (a coordinate, a count, a size, a table cell) or where nothing is known, as `unk_`/`XXX`. Messages are linker symbols written by bare name, `MSGNO(name)` their number. Flags and sounds come from `flags.h` and `songs.h`: `FLAG_`, `MUS_`, `SE_`, only proven names, an unproven sound its kind and number (`SE_138`); a temporary flag is `FLAG_SCENE_TEMP_xx` (cleared on entering a scene) or `FLAG_PLACE_TEMP_xx` (cleared on entering another place), with a comment per scene saying what it holds there.
  - Values are in the author's units (scene coordinates in pixels). Scenes are written in `event.h` commands.
  - Editions, as pret selects versions: C compares values from `edition.h` and `version.h` (`LANGUAGE == LANGUAGE_GERMAN`, `TBS_PATCH_1` to `_4`) and includes the header; only linker scripts, plain assembly (`ed_asm.h`) and `.S` files use edition names.
  - The model folder's conventions, for every folder:
    - Objects: an object over about 3,000 lines holding more than one family may be written as parts in `<object>/` beside its `.c`: the `.c` keeps a guide comment, includes a private header `<object>_internal.h` and then the parts in ROM order; each part includes the header and opens with what it defines. The header places no bytes (includes in their original order, macros, types, enums, externs, prototypes, `static inline` only); data and functions stay where the ROM order puts them. Data objects stay one file. A scene overlay stays one file, because its code is laid out by kind (entry points, then every handler, then every scene's tables), not by place; an overlay that holds more than one place (scene) opens with every place's area name, scene ids and what happens there, and each event's comment names the place it belongs to, from which the docs build one page per place. A split is its own commit, by one owner, before the folder is humanized.
    - One owner per fact: order in the guide `.c`, each part's summary on its first line, link order in `objects.tsv` (pointed to, never copied). A folder README gives its files, words and shared local names, its function prefixes, a Design section saying why its mechanisms are shaped as they are (in prose, with "XXX:" where the reason is unknown), how it fits with the rest of the game, its limits, and closes with its evidence and open questions; the plain-C spellings that match at different sites, and what the markers mean, live once in `games/tbs/src/MATCHING.md`. A ⚓️ folder's README says what differs from its ☀️ twin and links to it for the rest.
    - Prefixes: a function takes its folder's or family's prefix unless it acts on one thing the engine names elsewhere; a new prefix is added to the folder README, and a rename across folders is its own commit. A family takes its name from the function that reads it: the file, its tables (`g<Family>_`) and its macros (`<FAMILY>_`). Part-local macros, enum constants, struct tags, typedefs and statics start with the part's or a family's name; part macros take what they read as arguments and are `#undef`'d at the part's end; a macro two parts use goes in the private header.
    - Tables: a column enum sits above the first declaration its readers see (the definition in the same object, else the `extern`); a layout the ROM copies for several tables is one named initializer. Kinds index tables by an `enum` with designated initializers. A wrapper that calls a runner with a mode is a two-line function; a macro that generates functions is allowed where each generated name is written in full where it is used.
    - Entry points open with a one-sentence summary of what they do, then what reaches them, from the table that decides it (actflags.tsv's abilities and kind for effects, `/// Abilities: Quake, Earthquake (kind 1).`), then the rest of what the player sees, from evidence, then only the parameters that need saying; with no such table, no reach line.
    - Numbers with known meaning take names: search the shared headers first, put a name two objects use in a shared header, use macros or enums (never `const`), and keep the literal's type. Sizes are `(w * h)`, sheet offsets `*_CELLS` or the sum of the picture sizes before them, sounds `SE_`, registers composed from `io_reg.h` (`BLEND_ALPHA`, `BGCNT_*`, DMA flags `<< 16`), caps named once and used in their loop.
    - Editions: a value that differs by edition is a named macro chosen in one `#if` block at the top of its part or file, with a comment on what the player sees differ; an `#if` inside a function is for code whose shape differs.
    - Each idea has one preferred spelling; where a site matches only with a plain-C equivalent (index or pointer form, a macro or its expansion, a cast), that site keeps it untagged and `MATCHING.md` lists it. FAKEMATCH is only for S2's devices.
    - `// DEAD: why` marks code the ROM keeps that cannot change the result, only where the construct's own instructions (a compare, a branch, a loop) are in the ROM; it is then the source's form. Dead code that emits nothing and only steers allocation or order is a FAKEMATCH device, and turning one into DEAD names the instructions it emits.
    - Header guards are `ALCHEMY_<NAME>_H`. Comments go above the statement; a trailing comment only for a short note on a field or value.
- **S4** Never throw work away: commit each adoption and attempt; a near miss stays a draft with its remaining difference in its header, one draft per listing, a trial being a commit or a header line. An edition whose bytes differ stays on its scaffold and never blocks the others.

### Documentation

The docs are the folder READMEs, MATCHING.md, the `///` comments and the pages of `alchemy-docs`, published at alchemy.pascalpixel.com. People read them; AGENTS.md is the only file written for agents. Public readers have laughed at pages that read as generated, so each rule below comes from a page that failed.

- **D1** Purpose: the docs explain how the game works and how its parts fit together, a level above the code; whoever wants the code reads the code. They're not a modding manual (a modder works out changes from the code and the docs), a wiki (game facts appear where they explain code, never as catalogues) or a walkthrough. The test for anything on a page is whether it helps a reader understand some code.
- **D2** Story: a cutscene's code only makes sense against the story around it, so a scripted scene's account says where it falls in the story, as briefly as the code needs, and places and their events are presented in story order. The game's front page follows the story from its start in Vale to Venus Lighthouse being lit. The front page is `games/tbs/README.md`, and the site's four section pages sit beside it (`world.md`, `battle.md`, `menus.md`, `engine.md`): each opens from what the player sees, follows one thread through its questions with pictures, and points to the folder guides.
- **D3** Facts come from the game: every place, person and event a page names is checked against the game's text and data (`text/en.po`, `gScene_AreaNameRules`, the event tables) before it's written. A place takes its area name, a person the name the text gives, introduced as the game introduces them; nothing is described from the code's own words ("the raised warehouse approach" was the Bilibin Barricade, a "pillar" in a flooded cave a log); a room the game leaves unnamed is described by what its render and recordings show; and an internal number never stands in for a name ("Jupiter Djinni 0" is Gust).
- **D4** Pictures: a page with something to show shows it, so no page is a wall of text. Every picture comes from `alchemy-devtools render` on a tbs-en build and lives in `alchemy-docs/public`, never anything from `roms/`. A Psynergy cast, a summon and a Djinni get a GIF beside the code that plays them; a place gets a photo and a map per room beside its scene, with its variants; an event gets a GIF of each script segment between its messages; a scripted moment is shown as it plays (the town seeing Isaac and Garet off, Venus Lighthouse lighting up on the world map), never as the leader standing in the middle of a map. The front page shows the title screen and the whole world map.
- **D5** Writing: plain, warm English in connected sentences with contractions, as someone who knows the game and the code would write. The docs and comments speak to the developer reading them: whoever plays is the player (`Most of the village that night isn't the Vale the player walks around in later.`), never `you`, which is only ever the reader; quoted game text keeps its own words. A section starts from what the player sees and why the game needs it, then how it works, then the exact detail a contributor needs (bit layouts, hex values, symbols), explained the first time a page relies on it. Headings are the question a reader would ask ("What is a decompilation?") or the name every project uses ("Acknowledgements", "Progress tracker"), never a label ("What that means", "Try it", "How it's made"). No declarative fragments or labels posing as sentences ("World. Where the party walks.", "Shops: the counters.", "The questions people bring"), no formulaic openings ("This folder holds ..."), no process language (a page that "owns" a fact), no page describing itself.
- **D8** Numbers: the docs say what a number means, by the name the code gives it (`FIELD_WALK_SPEED`, `FLAG_FAST_WALK`, `MAP_LAYER_OVERHEAD`) and in the unit the player would use (pixels a frame, KB); a number the code doesn't name yet gets a name in the code first. Hex appears only where it is the data a reader will meet (a memory-map table, a value as a data file writes it), always in code formatting, and every register, layer or symbol (`BG1`, `REG_DISPCNT`) is in code formatting too. The same holds for comments: a comment cites the name, not the number.
- **D6** Repetition: what the project says about itself (that it rebuilds the games exactly, in six languages) is said once, in README.md. A sentence that every file, function or table would repeat is said once, at the layer or README it describes, and never in each `///` comment, since the site shows every one ("Part of effect.c, compiled only through it" appeared 234 times). Before landing a docs batch, count the phrases it repeats across pages.
- **D7** A folder's README.md is its page: it opens with a `#` heading unique across the repository that names the folder (`# Battle effects`), with a `{#label}` only where something links to it. Links between READMEs and code use relative paths and plain function names. The site's settings live in `alchemy-docs`, never as markup in the source.

### Assets

- **A1** Assets are editable files our tools build in every build, as pret's are: indexed PNGs with real palettes, TSV tables and tilemaps, WAV, MIDI, PO and text definitions; never raw dumps, grey sheets without a built palette, blobs or stored compression tokens. Each builds beside its source, ignored by git.
- **A2** A picture is drawn the way the game shows it: sheets at their real width or sprite shape, tilemapped pictures as the map shows them, animations one frame wide.
- **A3** An all-grey palette only where the build writes that palette from it.
- **A4** Encoder options live beside their assets; a recipe may carry a sprite shape in its name.
- **A5** No JSON: tables are TSV.
- **A6** Each edition combines its catalog, character map, fonts, metrics and layout with its measured code differences; differing resources are chosen in their owning module or build rule, and editions that agree are grouped. _Check: make compare-editions._

### Compilers

The set is frozen: three C generators built from the pinned `alchemy-gcc` submodule, six profiles, no research and no new compiler, option, route or alchemy-gcc commit. The one exception is a host fix that leaves every compile of the twelve editions byte-identical. Matching shows practical compatibility, not Camelot's exact compiler.

- **K1** Game Thumb C: alchemy-gcc (GCC of 2000-07-31) with `-O2 -mthumb -mcpu=arm7tdmi -nostdinc -fcall-used-r4`, plus `-mthumb-interwork` for ☀️ and K2's options for ⚓️; libgcc C with `-O2 -mthumb -mcpu=arm7tdmi -fno-inline`. ARM C: GCC 2.95.2 with `-O2 -mthumb-interwork -fomit-frame-pointer -fcall-used-r4`. Sound and flash: pret's `old_agbcc` (`-O2` and `-O`, `-mthumb-interwork`). The Makefile's SOUND_C, FLASH_C and ARM_C are the only routes; `make modern` adds none.
- **K2** ⚓️ adds, for every Thumb file, `-mthumb-split-constants`, `-mthumb-call-via-lr` and the stock `-mtune=arm9tdmi`, habits measured across its whole code; no other scheduler or allocator change. An instruction-order mismatch alone is no reason to change compilers.
- **K3** A compiler change needs one option set that explains most of a game's code, no public compiler of the time that already does, a plausible Camelot-style change with its evidence recorded here and in alchemy-gcc's README, and Pascal's approval.

### Work

- **W1** A plain Makefile whose every rule can be read; a build tool is a small tested C program for a step make cannot do; Rust only in the optional Alchemy Devtools; no TypeScript, JavaScript, Python or shell beyond a command line; tooling nothing needs is removed.
- **W2** Work on a branch; `main` is the only long-lived branch; land with `make land`.
- **W3** The Makefile owns compiling and linking, `tools/` the C encoders and small tools (`ags-` prefix), Alchemy Devtools the matching aids and count. Follow pret where it settles a question, and never be stricter: far-call banks are pinned per edition in the linker scripts; packer leftovers are tagged literal bytes beside their asset; each encoder takes one rule for all its streams, and a stream Camelot edited after packing takes a patch file of measured literals.
- **W4** Match first what other unfinished code calls, with the structures it shares, then the largest with nothing left to name.
- **W5** Before every commit, `make compare-editions` prints OK for all twelve editions.
- **W6** A change to what counts, a rule, an option or routing lands as its own commit with DONE before and after.
- **W7** Parallel work divides by owner; check a name is free (`git log --all -S`) before using it; when branches merge an adoption wins over edits to its draft; commit only verified work.
- **W8** Humanizing moves code toward S3 and keeps every edition byte-identical; message names stay linker symbols.

## What matching has measured

Not rules; facts about alchemy-gcc that keep coming back.

- `p[n]` and `*(p + n)`, and `&p[n]` and `&*(p + n)`, can compile differently: each site keeps the spelling it matches with.
- A struct object declared before its type is complete keeps a smaller alignment and changes the code that reads it: a header includes its structs' headers first.
- alchemy-gcc pads every struct to 4 bytes, and a field after the first is addressed from the table's base: a table read by columns is a `[][N]` array with an `enum` naming the columns.
- Locals declared in an inner block take their pseudos later and change register allocation.
- A file that tests `LANGUAGE` without including `edition.h` silently gets the Japanese branch.
- Within one object, code and data follow definition order after preprocessing; only the object list orders objects. Every Thumb function starts on 4 bytes, so code shows no object boundary; data can, through a gap no type alignment explains.
- Register choice is arithmetic: allocation order r3, r2, r1, r0, ip, lr, r4 to r7, r8, r10, r9, r11; global.c ranks pseudos by refs and live length, loop depth weighting refs. A constant `REG_EQUAL` note doubles a pseudo's live length.
- An empty asm counts 4 estimated bytes when arm_reorg places literal pools, and emits none. A one-pass block's loop-end note ends CSE's block and is a scheduling barrier; sched2 breaks ties by RTL order. A halfword constant that survives to a register loads from the pool.
- CSE reuses a register holding 0 or 1, so a native store of a register is often a constant in the source. Unused locals do not make frame gaps; allocation does.
- Japanese is often an older layout of a function with its own `#if`, or stays on its scaffold. Nested functions adopt with their parent. A function that saves r9 and never uses it is a nested function storing its static chain.
- ⚓️ near misses: of 796 drafts, 400 differ only in instruction order and 48 only in register choice; the native most often issues a literal-pool load earlier than alchemy-gcc. That corpus is where a K3 question about ⚓️'s scheduling would start. Another row recurs: after a store, the native puts some other instruction (often the second half of a constant) before a load through a different base, where alchemy-gcc issues the load at once; no single barrier reproduces it. A one-pass block holding the statement before a pool load and the assignment that needs it can move the load up (BattleFx_UpdatePairedArcSpawner).
- To measure a rewrite in seconds, compile its one object to assembly for one edition with the Makefile's command and diff it against a baseline with `.L` label numbers ignored; then `make compare-editions`.
- Builds from another branch leave `out/*/deps.mk` and `out/*/objects.mk` that break this one: delete them. After switching to a branch whose tools differ: `rm -rf tools/out/obj tools/out/ags-* && make tools`. In zsh, a variable holding several flags is one word unless written `${=VAR}`; `git grep -E` has no `\b`, so use `-w`.
