# `resource_379` scene setup (`0x02000074`)

## Status

Excluded from the semantic-C reconstruction for now. No C source is claimed.

The ordinary region beginning at `0x020000dc` is not an independent function.
It is a shared entry into the routine whose normal entry is `0x02000074`.
The shared entry has no prologue and returns through the enclosing routine's
saved-register frame:

```text
0x02000074  push {r5, lr}
...
0x020000dc  shared scene-setup body
...
              pop {r5}
              pop {r0}
              bx r0
```

`Func_02000054` can branch into that shared body after establishing the
compatible frame. Consequently, a standalone `Func_020000dc` in ordinary C
would invent a callable ABI that the overlay does not have.

## Reconstruction result

The complete `0x02000074` control flow was recovered as a long, mostly linear
scene-construction script:

- 276 calls through overlay-local trampolines;
- two result-dependent branches;
- two increments of the halfword at scene-state offset `0x1d8`;
- initialization and finalization writes at scene-state offsets `0x1c0` and
  `0x1c8`;
- a shared body entered both from `0x02000074` and `0x02000054`.

The available automatic draft also leaves several PC-relative literal loads
unresolved. Replacing those values with guesses or zeroes would compile, but
would not be behaviorally faithful.

## Safe next step

Recover this as one source-owned unit containing:

1. a private scene-setup body for the code from `0x020000dc` onward;
2. a normal-entry wrapper for `0x02000074` that performs the preceding setup;
3. the `0x02000054` selector expressed against the same private body.

Before admission, identify every PC-relative literal from the decompressed
overlay image and map the trampoline calls to shared, typed engine APIs. This
avoids preserving a fabricated internal-entry calling convention in C.
