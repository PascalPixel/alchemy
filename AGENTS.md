# Alchemy

It instructs the agents that work on Alchemy; people read `README.md` and `INSTALL.md`. The agents keep it current, wording included. Pascal decides compilers, what counts as DONE, and deleting anything that cannot be restored; everything else goes ahead without asking, including fixing a check that wrongly blocks honest work as long as it still refuses everything it refused before.

Alchemy rebuilds Golden Sun: **The Broken Seal** (☀️, build `tbs`) and **The Lost Age** (⚓️, `tla`) byte for byte from readable C, assembly and editable assets, in Japanese, English, German, Spanish, French and Italian: twelve editions, `tbs-ja` to `tla-it`. Japanese releases are the source editions; localizations are measured differences.

## Goal

- **DONE** is a pair, counted over all six editions of a game (C2): code (matching C and proven assembly) and data (bytes placed from source). **100%** is pret's standard, never stricter: all six editions build byte-identical from source and anyone can verify them from `rom.sha1`; DONE code and data are both 100%; no function is matched by an assembly body or inline asm beyond the proven `CAMELOT_ASM` helpers; nothing in the build reads a ROM, confirmed by an independent audit (O4); the C compiles with a current GCC (`make modern`); every steering device is tagged and counted. ☀️ has reached it; ⚓️ is still being matched.
- **Finished** means more: every asset ported (A1), `recon/<game>` gone, no FAKEMATCH device left, a limited set of stock compilers (K1 to K3), and every system and map humanized (H4).
- **Humanized** means a reader can learn how the game works from its source: each system, map and script says what it is and why, under the name the game gives it, with its data read through types, and the docs are written from that source (H1). It is reached one system or map at a time, all the way through, starting from finding out what the thing is (H2); the humanity count is a worklist, not the definition (H5).
- PostgreSQL at `~/Developer/postgres/postgres` is the humanization quality reference: comments explain purpose, invariants and ownership, proven numbers have names, and formatting is consistent. Alchemy keeps S3's C89, naming and formatting conventions and D9's comment forms; `games/tbs/src/battle_anim` shows its local forms.

## Where things are

- Source: `games/<game>/src`, `include`, `sound` and `text`; each game owns its copy of what it uses (its engine headers in `include/<folder>`, ⚓️'s copies of ☀️-numbered assets under ⚓️'s own numbers), and sharing may be revisited when both games are complete. ☀️'s code sits in one folder per bank of the main image (`runtime`, `field`, `window`, `game`, `menu`, `shop`, `battle`, `battle_anim`, `overworld`) beside `graphics`, `layout`, `sound`, `system`, `debug` and `map` (each map overlay is `map/<map>.c` with `map/entry/` and `map/import/` tables; ⚓️'s are still folders under `scene/`). Unit headers follow the same paths under `include/unit`.
- `games/<game>/objects.tsv` lists every object in link order with its sections and editions; `games/<game>/main.ld` is the one main script, chosen by `--defsym <GAME>_EDITION_<LANG>=1`. ☀️'s overlays link through `games/tbs/src/system/overlay/overlay.ld`; ⚓️'s are one script each under `recon/tla/raw/overlays`.
- `recon/tla` holds ⚓️'s not-yet-C work: `raw/` listings, `<lang>/` scaffolds, `en/main/<address>.c` drafts. ☀️ has no `recon/`.
- `games/tbs/src/battle_anim/battle_anim.c` is one object written as parts: it includes `battle_anim_internal.h`, the private header every part also includes, then the files under `battle_anim/parts/` in ROM order (S3).
- The `Makefile` builds everything; `tools/` holds the small C programs it runs (`ags-*`); the optional `alchemy-devtools` submodule holds the Rust matching aids and the progress count. `out/` and `tools/out/` are build output.

## Commands

Setup is in `INSTALL.md`; ROMs go under `roms/` as `tla-ja.gba` and so on, checked against `rom.sha1`, never committed.

```sh
git submodule update --init --recursive alchemy-gcc
make bootstrap         # the tools, the pinned compilers, GAS 2.10 and libgcc
make compare-editions  # all twelve editions: required before every commit (W5)
make -j8 compare-tbs   # the six ☀️ editions; compare-tla-en for one edition
make modern            # ☀️'s C with a current GCC: no errors
make test              # the build tools' tests
git submodule update --init alchemy-devtools && make devtools  # optional, Rust
git config core.hooksPath .hooks   # send verified measurements when pushing main
make progress          # DONE code and data (C2)
make land              # on main, before a landing (W2, C3)
alchemy-devtools/target/release/alchemy-devtools diff DRAFT.c [ADDR] [--show|--heat|--rtl]
alchemy-devtools/target/release/alchemy-devtools permute DRAFT.c [ADDR] [--minutes N]
```

`make compare-editions` prints a lot: send it to a log file and count the `: OK` lines.

## Boundaries

Always: keep all twelve editions byte-identical (W5, W8); tag every compiler-steering device with its measured difference (S2); name only from evidence (H3); commit each verified step, attempts included (S4, W7); look at how pret does it first (W3).

Ask Pascal first: any compiler, option, routing or alchemy-gcc change (K1 to K3); anything that changes what counts (C2, W6); deleting what cannot be restored; pushing, pulling, fetching or publishing outside the verified humanization sync authorized in Workflow 6.

Never: commit or publish a ROM or game files (L1); use another project's Golden Sun work (L2), or leaked Nintendo or Camelot code or SDKs or anything derived from them (L3); let the ROM steer the build or count (O1); write a function as inline assembly, place data through `asm()` (S1), patch compiler output or give a function its own compiler option (S2, K1); treat old history or deleted files as evidence (O5); add JSON, Python, shell or TypeScript programs (A5, W1).

## Workflow

1. Work in the main checkout on a branch; `main` is the only long-lived branch, and Pascal prefers no worktrees (W2).
2. Match what other unfinished code calls first, then the largest with nothing left to name (W4).
3. Draft in `recon/<game>/en/main/<address>.c`; a near miss stays a draft with its remaining difference in its header (S4).
4. Adopt a match into the module of its linker neighbours, in every edition whose bytes agree, and commit (C1, S4).
5. Humanize one system or map at a time, all the way through, each step byte-identical (H2).
6. Land with `make land`; Pascal authorizes syncing each verified humanization batch on local `main` to `origin/main`, including its progress measurement (W2, C3). Other pushes need his request.

## Rules

### Legal

- **L1** Never commit, upload or publish a ROM, private inputs or any copy of the game files. The cartridge logo lives only in the header fix-up tool, `ags-header`, as in pret's gbafix.
- **L2** Evidence is our own ROMs, this repository and public documentation. Never use or open another project's Golden Sun work.
- **L3** Never use leaked Nintendo or Camelot code or SDKs, and never open, read or mention sources that might contain them, nor anything derived from them.

### Counting

- **C1** A function counts only when its whole extent, literal pool included, compiles exactly and every edition stays byte-identical, and in an edition only when that edition links its C. _Check: make compare-editions._
- **C2** DONE is pret's calcrom over the linker maps, by folder: bytes placed from `games/` are done, from `recon/` not yet. Each image counts from its first to its last placed byte (overlays once, unpacked). Code is `.text` (C, assembly, 8-byte stubs and the compiler library reported apart); data is everything else. A game's figure sums its six editions; 100% needs both at 100% in all six.
- **C3** Every push to main carries its measurement: stage all source changes, then `make land` compares, tests and measures the same tree; the pre-push hook uploads immutable reports and their timestamped receipt to `decomp-reports`. `make land` also runs the tool tests, the format check and `make modern`; CI then proves only what anyone can check without our machines: the six ☀️ editions rebuild from a clean clone with no ROM. After that build passes, CI validates the receipt, archives the figures, accepts the measurement and starts the `alchemy-docs` site build on Vercel through a deploy hook; that site serves the docs and README's figures. The old `progress` branch is a frozen archive, never updated. `.github/publication.md` describes publication and recovery.

### The oracle stays out of the build

The reference ROM judges the build and never feeds it. Reconstructing Camelot's compiler from habits across a whole game is allowed (K3); fitting a compiler, option or routing to particular functions is cheating.

- **O1** ROM bytes reach the build only through pret's `.incbin "baserom.gba"` scaffold in `recon/`, which never counts, and the logo `ags-header` writes. Nothing else derived from the ROM or expected output steers the build or count; `out/` reports are for people only.
- **O2** Every name is defined where its bytes are; layout is the object list order. No equate, alias, `#define` or table gives a name an address, except Camelot's own fixed addresses (resident IWRAM routines, RAM buffers addressed as constants, the cartridge restart entry), each listed once and checked against the link. One name per place. An assembler equate (`.equ`, `.equiv`) holds only what its own table computes (a row's position, a table's length) or a value its evidence names, as a `#define` would need; a size or constant set only so the bytes come out right is a copied byte (S1). `.set` only switches assembly in or out (an overlay's imports, the edition).
- **O3** Map and resource ids come only from their tables, used whole. Overlay code never branches straight into the main image.
- **O4** A mismatch is fixed in source, or the code stays a draft. Before a milestone, run an independent audit for leaks.
- **O5** Old git history, deleted files, backups and unreachable objects are never evidence.

### Humanizing

Humanizing is research before it is writing: the work from 19 to 21 October 2026 renamed the bush that was ivy, the pillars that were logs, the officials who were soldiers and `Summon_IsEntryFlagged`, which was `BattleClass_IsSmall`, each because it had been named and commented before anyone knew what it was. A pass over the whole tree for one rule, done before the things it touches are understood, is redone when they are.

- **H1** Purpose: a reader learns how the game works from its source. Each system, map and script says what it is and why, under the name the game gives it, with its data read through types, and the docs are written from that source (D1). The bytes stay identical; nothing has to look like the original's source, and our names are never presented as recovered.
- **H2** Unit and order: the unit is one system (a family or a mechanism: the sound driver, the Djinn menu, the scheduler) or one map (an area and its scripts, in story order). Take a unit all the way through, in this order, since each step needs the one before:
  1. Find out what it is: its callers and data, the game's text (`text/en.po`), its tables, its area name, and what `alchemy-devtools render` and recordings show. What isn't settled stays a placeholder with `XXX:` and the evidence that would settle it.
  2. Type it: data read through the engine's structs, kinds and modes as enums, prototypes and signedness from the program (S3).
  3. Name it from that evidence (H3), with its meaningful numbers (S3).
  4. Shape it: fold repeats into the game's own helpers and macros, group its files, and clear what the matching left behind (S3's original behaviour, stale devices, `goto` that only forced a layout).
  5. Explain it: comments and its README page (D1 to D9), with a recording or screenshot where one helps (D4).

  Work that needs no understanding (formatting, `make modern` warnings, the Doxygen form, moving files) may run across the tree at any time; names and comments may not.
- **H3** Evidence: a map takes its area name from `gMapSec_NameRules` (`overworld/map_rules.s`, read through `MapSec_GetNameIndex`, an offset from `MsgDebugEntryName` in `text/en.po`; ⚓️ still spells them `gScene_AreaNameRules` and `Scene_GetAreaNameIndex`); a character the name the game's text gives, introduced as the game introduces them. A room the game leaves unnamed is named, and its comment written, by what the player sees there and what sets it apart (CrossboneIsleFloodgate, for the floodgate the player closes to float its logs), checked against its render and recordings. The code's own words for a thing (a "raised warehouse approach", a "pillar") are a guess about it, never its name. Game terms are the English release's: Psynergy is uncountable ("uses Psynergy", never "a Psynergy" except before another noun, as in "a Psynergy Stone"); one Djinni, several Djinn; what Move pushes is a stone pillar ("It's just a stone pillar."), or an ice pillar where Frost makes one, never a block, which is a block of memory (a map's 16-pixel picture is a metatile). A name of a place, person or thing carries its evidence in one line of its `///` comment, opening with ★ and in one of three forms a tool checks: `★ Named from the game: "Please... Don't leave me all alone..." (MsgValeMomDadFelixPleaseDontLeave)`, `★ Named from its area name: Bilibin Barricade`, or `★ Named from what the player sees: the floodgate the party closes to float its logs (its render)`. A game-thing name without that line is unchecked; the docs show ★ beside the names whose line checks out. Names of code mechanisms need no line: the code is their evidence.
- **H4** Done: a unit is humanized when no placeholder remains that its evidence could settle; its data is read through types, not offsets and casts, wherever a match allows; every value with a meaning has a name; what the game can't reach says so (S3); its comments and README page meet D1 to D9; and every open question is an `XXX:` saying what evidence would settle it, gathered in its README's closing section, `## Evidence and open questions` (for a map, at the end of its overlay's opening `/// @file` comment, under the line `Open questions:`, which reads `Open questions: none.` once the last is settled, so the unit counts as done rather than unstarted). FAKEMATCH devices and `goto` never rise (S2). There each open question is one list item in one of two forms a tool can count: `- XXX: <question>; <the evidence that would settle it>.` for work still to do, and `- XXX (no evidence): <question>; <why nothing in reach settles it>.` for a question only evidence beyond the ROM and our renders could settle. A unit whose section holds no `- XXX:` item is done. A map's list doesn't ask what a sound is: `songs.h` owns sound names, and an unproven sound keeps its kind and number (S3).
- **H5** Rules and counts: `alchemy-devtools progress --humanity` lists what may still need work. Its `units` and `units_done` rows count the units and those done under H4, and every unit done is the target; `--list unit_open` is the worklist. Where a count asks for something these rules forbid (a `///` a reader could rebuild from the name, a name for a wait in frames or a coordinate, a split of a map overlay), the count is wrong: leave the code and fix the count. A wrong name is fixed where it is; it becomes a rule only when it shows a principle the rules here miss, and then the rule is written once, where it belongs, replacing any narrower rule it covers.

### Source

- **S1** `games/` holds only real source: C from an approved compiler, or proven assembly written as instructions, never copied bytes. Assembly is proven as the compiler library, as whole 8-byte far-call stubs, or as handwritten, which it is only with an instruction, frame or pattern alchemy-gcc cannot emit (rrx; a branch, adc or sbc on a shift's carry; r11 as an ordinary register; a callee save without lr; CPSR/SPSR; swi; computed pc into code; stores into code; unpaired multiply halves; a pc-relative block load of data; a mode switch inside a function; movs with no shift; ldm or stm writing back off sp other than a block copy from r0 or a doubleword pair; a conditional branch on flags with no compare; one literal pool shared by two functions) or a linkage no procedure-call standard produces. Anything else stays in `recon/` until it matches as C. Data is a C definition or a table in a `.s` file: no C file places bytes through `asm()` (a `.section`, `.byte` or `.incbin` inside one), whatever the bytes are.
- **S2** Compiler-steering devices, by kind (`wrapper`, `volatile`, `temporary` for a forced temporary, `dead` for dead code, `one-pass` for a once-only block or loop, `barrier` for an empty asm, `pin` for a fixed-register variable, `signature` for a function declared with a return or parameter type it doesn't have, such as a `void` function typed `int`), count, as in pret, when each carries a tag inside its function in one form, `/* FAKEMATCH(<kind>): the form kept; as <plain form>, N of M instructions differ in tbs-en. */`, where the kind is one of the devices listed here and N comes from a whole-function `alchemy-devtools diff` (or the function's instructions in its object's assembly) against the edition named; dates and attempts go in commit messages; removing them is humanizing. In ☀️ their counts, and the count of `goto`, may only fall; ⚓️, whose compiler is not yet right, may add tagged devices to reach a match (Pascal); trading one device for another is no progress unless the new form is the source's. A device is for instruction order, register choice, a frame gap one unused local of a real type explains, or a form the bytes prove the source had; it comes only after reshaping has failed, and a function is never inline assembly. A `pin`, a `one-pass` block and a `signature` hide the source's shape rather than steering one instruction, so they come last: ⚓️ adds one only where no other device matches, and they are the first ☀️ removes. A `goto` is plain C and untagged, but one that only forces a layout goes when its loop is found. `CAMELOT_ASM("proof")` marks the proven handwritten helpers inside C: `Dma_Set`, `Transform_SetIdentity`, `Iwram_Call2`, `WaitFrames`' stack switch, `MulQ16`, and the `swi 2` and `swi 3` BIOS calls. A layer that explains a habit of the whole game is source, not a device: the ☀️ map script layer (`script_layer.h`, `field_service.h`; ⚓️'s `field_event.h`), the IWRAM call layer (`iwram_call.h`) and the engine call layer (`engine_call.h`). A statement macro takes the shape its sites match with: `do { } while (0)` is no device where every use matches through it, but it compiles as a one-pass block in alchemy-gcc, so comma expressions and plain `{ }` blocks are often what match; a device inside a macro counts at each use. Never patch compiler output.
- **S3** Source conventions: readable modern C in English, as pret writes its games.
  - Layout: lowercase, short file names, the same folders in both games; `NAME.S` is assembly the C preprocessor reads, `name.s` plain assembly. Rename a file with its includes and object list rows. Each game keeps its own copy of code both use; a function goes into the module of its linker neighbours.
  - Objects: an object over about 3,000 lines holding more than one family may be written as parts in `<object>/` beside its `.c`: the `.c` keeps a guide comment, includes a private header `<object>_internal.h` and then the parts in ROM order; each part includes the header, is one family or run, opens with what it holds, then a plain `// Part of <object>.c.` line; the parts are ours, not Camelot's files. The header places no bytes (includes in their original order, macros, types, enums, externs, prototypes, `static inline` only); data and functions stay where the ROM order puts them. Data objects stay one file. A map overlay stays one file, because its code is laid out by kind (entry points, then every handler, then every map's tables), not by map; an overlay that holds more than one map opens with every map's area name, map ids and what happens there, and each script's comment names the map it belongs to, from which the docs build one page per map. A split is its own commit, by one owner, before its unit is humanized. One owner per fact: order in the guide `.c`, each part's summary on its first line, link order in `objects.tsv` (pointed to, never copied).
  - Language: C89 with the GNU extensions the compilers accept, `//` comments included; prototypes, `typedef`, `enum`, structs; types, signedness and scopes from the program and the matching evidence. Data is read through the engine's structs and enums rather than offsets and casts wherever a match allows.
  - Naming, as pret's: functions `PascalCase`, globals `gName`, file statics `sName`, constants and macros `UPPER_SNAKE_CASE`, locals and fields `camelCase`; game things are named from evidence (H3). A name says what the thing does; an unknown stays a placeholder (`sub_08012345`, `unk_14`).
  - Vocabulary: a concept keeps one name everywhere, pret's (pokeemerald's) word where pret has the concept, else the game's word where the player sees it, else a common game-development word; `games/tbs/names.tsv` records each word with its source and evidence, and a new concept word is added there first. The map layer says map, map header, map section, layout, metatile, metatile behavior, warp, warp destination, object event, local id, coord event, bg event, script; the engine says heap slot (its global `g<Slot>Work`), task, object (one of the 64 in `gObjects`), sprite, sprite anim, window, text printer, song, palette fade, scanline effect; the screens are the main menu, option menu, pause menu, field menu, summary screen, naming screen, file menu and region map; a battle has units (a member is a unit in the party), formations, rounds of turns, battle actions, a playback queue and battle animations, and the game's own words name what the player sees (Psynergy, Djinn set and on standby, Lucky Wheels, Battle Arena, Sanctum). "Scene" means only a cutscene, "slot" only a place in a fixed array, "resource" only the resource directory, "channel" only the sound driver's, "record" only a save record, "effect" only an ability's rules effect, an equip effect or a field effect, and "event" only map events and their scripts. ⚓️ keeps the older words (scene, place, actor, exit, entrance) until its own pass.
  - Prefixes: a function takes its folder's or family's prefix unless it acts on one thing the engine names elsewhere; a new prefix is added to the folder README, and a rename across folders is its own commit. A family takes its name from the function that reads it: the file, its tables (`g<Family>_`) and its macros (`<FAMILY>_`). Part-local macros, enum constants, struct tags, typedefs and statics start with the part's or a family's name; part macros take what they read as arguments and are `#undef`'d at the part's end; a macro two parts use goes in the private header.
  - Original behaviour: undefined behaviour keeps its form with the defined one behind `UBFIX`; original bugs keep their code with pret's `// BUG:` and a fix behind `BUGFIX`. `// DEAD: why` marks code the ROM keeps that cannot change the result, only where the construct's own instructions (a compare, a branch, a loop) are in the ROM; it is then the source's form. Dead code that emits nothing and only steers allocation or order is a FAKEMATCH device, and turning one into DEAD names the instructions it emits.
  - Unused: a function nothing refers to is `UNUSED`. What the game can never reach (a map no cell or table leads to, a branch its flags rule out) opens its comment with `Unused:` and says why and what the player would have seen; the docs head it "(unused)". Where it holds something the player would have seen (a script, a map, its tables), its name carries `Unused` right after its family prefix (`EventScript_UnusedGaretJoinsIsaac`, a table `gValeStorm_UnusedGaretPantingScript`); a helper nothing calls keeps its name, since `UNUSED` already says it. What only the debug menus reach is not unused: its comment says the debug menus reach it, and its name stays.
  - Numbers stay numbers until evidence gives them a meaning; a constant never invents an address or table id. Once a value has a meaning it has a name, and neither code nor comments use its number again: a map is its `MapId_` (`MapId_UnusedMercuryLighthouseAerieCopy`, never "map 59"; ⚓️: `SceneId_`), an element its `ELEMENT_` name or "the four elements" (never "element 0 to 3"), a door its `map_warps.h` name (⚓️: `scene_links.h`), a mode, state, kind, slot, variant or metatile behavior its enumerator, and a `switch` on such a value switches on those enumerators. A value with a meaning and no name yet gets an enum before the comment about it is written. A number appears only as data (a coordinate, a count, a duration, a size, a table cell) or where nothing is known, as `unk_`/`XXX`. Names go in the shared headers first (a name two objects use lives in one), as macros or enums (never `const`), keeping the literal's type. Sizes are `(w * h)`, sheet offsets `*_CELLS` or the sum of the picture sizes before them, registers composed from `io_reg.h` (`BLEND_ALPHA`, `BGCNT_*`, DMA flags `<< 16`), caps named once and used in their loop. Messages are linker symbols written by bare name, `MSGNO(name)` their number. Flags and sounds come from `flags.h` and `songs.h`: `FLAG_`, `MUS_`, `SE_`, only proven names, an unproven sound its kind and number (`SE_138`); a temporary flag is `FLAG_MAP_TEMP_xx` (cleared on entering a map) or `FLAG_MAPSEC_TEMP_xx` (cleared on entering another map section), with a comment per map saying what it holds there (⚓️: `FLAG_SCENE_TEMP_xx`, `FLAG_PLACE_TEMP_xx`).
  - Values are in the author's units (map coordinates in pixels). Scripts are written in `script.h` commands (⚓️: `event.h`).
  - Tables: a column enum sits above the first declaration its readers see (the definition in the same object, else the `extern`); a layout the ROM copies for several tables is one named initializer. Kinds index tables by an `enum` with designated initializers. A wrapper that calls a runner with a mode is a two-line function; a macro that generates functions is allowed where each generated name is written in full where it is used.
  - Editions, as pret selects versions: C compares values from `edition.h` and `version.h` (`LANGUAGE == LANGUAGE_GERMAN`, `TBS_PATCH_1` to `_4`) and includes the header; only linker scripts, plain assembly (`ed_asm.h`) and `.S` files use edition names. A value that differs by edition is a named macro chosen in one `#if` block at the top of its part or file, with a comment on what the player sees differ; an `#if` inside a function is for code whose shape differs.
  - Spellings: each idea has one preferred spelling; where a site matches only with a plain-C equivalent (index or pointer form, a macro or its expansion, a cast), that site keeps it untagged and `games/tbs/src/MATCHING.md` lists it. FAKEMATCH is only for S2's devices.
  - Formatting: clang-format's LLVM style, as `.clang-format` records it; include order is left alone, since it decides which declarations are in scope. Header guards are `ALCHEMY_<NAME>_H`.
- **S4** Never throw work away: commit each adoption and attempt; a near miss stays a draft with its remaining difference in its header, one draft per listing, a trial being a commit or a header line. An edition whose bytes differ stays on its scaffold and never blocks the others.

### Documentation

The docs are the folder READMEs, MATCHING.md, the `///` comments and the pages of `alchemy-docs`, published at alchemy.pascalpixel.com. People read them; AGENTS.md is the only file written for agents. Public readers have laughed at pages that read as generated, so each rule below comes from a page that failed. A unit's comments and page are its last step (H2): they are written from what the earlier steps found, never ahead of it.

- **D1** Purpose: the docs explain how the game works and how its parts fit together, a level above the code; whoever wants the code reads the code. They're not a modding manual (a modder works out changes from the code and the docs), a wiki (game facts appear where they explain code, never as catalogues) or a walkthrough. The test for anything on a page is whether it helps a reader understand some code.
- **D2** Shape: every page has the same shape, so a reader knows where to look and a search lands on the right section. A mechanism (one thing the code does: the heap, a cue's range, the canvas transfer) is one section headed by its name, and runs in this order, leaving out a step it has no material for: one sentence saying what it is and what it is for; a recording or screenshot of it where seeing the game helps (D4); how it works, in the order control passes, with the invariants it keeps and why; the code that does it, by plain function name in call order, with a few lines quoted only where they say more than prose; the data it reads (its tables, structs and files); and a table of its names and values (name, value, meaning, in the player's units), each checked against the code. A mechanism's parts are `###` sections of the same shape. A folder guide runs: its heading, then a paragraph on what the folder is for; its mechanisms, `##` each, in the order control passes through them; `## Design`, for reasons that span several mechanisms; `## How it fits with the rest of the game`; `## Limits`; its reference, `## Files`, `## Words used here` and `## Function prefixes`; and last `## Evidence and open questions` (H4). The front page, `games/tbs/README.md`, explains the game's top-level structure (the main loop, maps and overlays, flags, the banks of the main image); the four section pages beside it (`world.md`, `battle.md`, `menus.md`, `engine.md`) each explain one layer, a mechanism to a section in the same shape, shorter, ending with a link to the folder guide's section, then `## Limits`. `glossary.md` beside them defines the words every page shares, in the order a newcomer meets them (the game's, the project's, the engine's, the maps'): one `###` entry each, a sentence or two and a link to the section that explains it. The story appears only where the code depends on it (a map that reads story flags to choose who stands where), in one sentence that places it; lists of maps and scripts follow story order, since the flags impose it.
- **D3** Facts come from the game: every place, person and event a page names is checked against the game's text and data before it's written, and named as H3 names it. Nothing is described from the code's own words ("the raised warehouse approach" was the Bilibin Barricade, a "pillar" in a flooded cave a log), and an internal number never stands in for a name ("Jupiter Djinni 0" is Gust).
- **D4** Pictures: the docs' pictures are the game itself, showing what the player sees: a recording or screenshot from `alchemy-devtools render` on a tbs-en build, published to the `alchemy-renders` Blob store with its manifest committed (`alchemy-docs/README.md`) and referenced by its `https://alchemy.pascalpixel.com/` URL, with no text baked into its pixels. A recording is for the game in motion (a walk, a battle, a Psynergy cast), a screenshot for what holds still (a place, the world map). A page uses one where seeing the game explains the code, and needs none otherwise; what no picture shows, the prose says. Never a hand-drawn diagram or illustration (Pascal removed every SVG: they read as generated and added no understanding), never a data dump (byte grids, register charts, numbered object events, raw layout grids, memory static, all rejected though correct), never Mermaid. The generated place and ability pages keep their recordings.
- **D5** Writing: plain English a curious reader who has never seen the code can follow, as `games/tbs/src/field/README.md` is written. A page and each section open from what the player sees and why the game needs it ("While the party walks around a town, the game asks once a frame whether something should happen"), then how it works in plain words, then the exact detail a contributor needs (symbols, bit layouts, tables), with function names as references rather than the words a sentence is built from. Say what a thing is, the rule it keeps and why, with `XXX:` where the reason is unknown. No narration, mood or retelling of the plot, and no sentence there to read well rather than to inform. Whoever plays is the player; `you` is only ever the reader; quoted game text keeps its own words. Headings name their subject ("Walking and running") or ask the reader's question ("How high a step can go"), never a label ("What that means", "Try it"). No fragments posing as sentences, no formulaic openings ("This folder holds ..."), no process language, no page describing itself.
- **D6** Repetition: what the project says about itself (that it rebuilds the games exactly, in six languages) is said once, in README.md; the glossary defines its words (matching, the editions) for readers who arrive on another page. A sentence that every file, function or table would repeat is said once, at the layer, macro or README it describes, and each site keeps at most a short tag pointing to it ("Part of battle_anim.c, compiled only through it" appeared 234 times). Before landing a docs batch, count the phrases it repeats across pages.
- **D7** A folder's README.md is its page, in D2's shape: its `#` heading is unique across the repository and names the folder (`# Battle effects`), with a `{#label}` only where something links to it; `## Design` says in prose why its mechanisms are shaped as they are, with `XXX:` where the reason is unknown. A summary over about 15 lines that describes a family belongs there, with a pointer from the code. A ⚓️ folder's README says what differs from its ☀️ twin and links to it for the rest. Every page links a glossary word at its first use, once, with a relative link to its entry, and a word two pages use undefined goes into the glossary first. Prose names the games, never ☀️ or ⚓️, and cites no rule of this file. Links between READMEs and code use relative paths and plain function names; a heading other pages link to is renamed only with those links. The site's settings live in `alchemy-docs`, never as markup in the source.
- **D8** Numbers: the docs say what a number means, by the name the code gives it (`FIELD_WALK_SPEED`, `FLAG_FAST_WALK`, `MAPGRID_LAYER_OVERHEAD`) and in the unit the player would use (pixels a frame, KB); a number the code doesn't name yet gets a name in the code first. Hex appears only where it is the data a reader will meet (a memory-map table, a value as a data file writes it), always in code formatting, and every register, layer or symbol (`BG1`, `REG_DISPCNT`) is in code formatting too. The same holds for comments, which cite the name, not the number. Prose says in words what a value means, by the name the game or the code gives it (a cell is a wall, the door into Isaac's house or the push that moves a log, never its metatile behavior's number, which readers of `guides/scene/event-cells.png` could not decode), and a count or duration keeps its unit (frames to the next change).
- **D9** Comments: English, short, saying what the code cannot (what the player sees, units, why a forced form is forced, the evidence for a name).
  - A comment a reader could rebuild from the name, signature or body is deleted, not reworded, and a declaration that needs no comment gets none; a comment on a statement explains a condition, order or constant the code does not show. Comments go above the statement; a trailing comment only for a short note on a field or value.
  - A function's comment says, where the code shows it, who reaches it and what state it changes; when the reason for an unusual form is known it says why, and when it is not, `XXX:` says so and what evidence would settle it. A hedge is only `XXX: likely X, because Y`.
  - An entry point opens with a one-sentence summary of what it does, then what reaches it, from the table that decides it (ability_anims.tsv's abilities and kind for effects, `/// Abilities: Quake, Earthquake (kind 1).`), then the rest of what the player sees, then only the parameters that need saying; with no such table, no reach line.
  - A field gets a `///<` note as soon as anything about it is known, placeholders included; packed bits get a one-line bit layout (`/// bits: 7 battle | 6 field | 3..0 kind`). FAKEMATCH tags say what they steer, in at most three lines.
  - Form, in Doxygen's line style: a comment that documents a declaration (a file, function, global, type, struct, enum, macro or field) is `///`; every other comment stays `//`. A trailing note on a declaration is `///<`, its continuation lines too. No `@brief`: Doxygen takes the first sentence. No `@param` or `@return` unless a parameter needs saying; then `@param name` with the sentence that already said it. The first sentence is the summary: it ends before any quoted game text and holds no abbreviation with a full stop ("e.g.", "Mt."). Message blanks go in backticks (`` `<unit> takes <damage> damage!` ``).
  - A file's opening comment is `/// @file` with its summary on the `///` lines after it; a file with none gets none invented. A part's `@file` says what it holds; the plain `// Part of <object>.c.` line after it names its object, and the folder README says once how parts are compiled.
  - FAKEMATCH tags, `// BUG:`, `// DEAD:` and comments inside function bodies stay `//`: they describe matching, not the interface. So do a block a blank line separates from what follows, a section heading or label over a run of declarations, a comment above `#if` or `#include`, and `// clang-format off` and `on`, which clang-format reads only in that form.

### Assets

- **A1** Assets are editable files our tools build in every build, as pret's are: indexed PNGs with real palettes, TSV tables and tilemaps, WAV, MIDI, PO and text definitions; never raw dumps, grey sheets without a built palette, blobs or stored compression tokens. Each builds beside its source, ignored by git.
- **A2** A picture is drawn the way the game shows it: sheets at their real width or sprite shape, tilemapped pictures as the map shows them, animations one frame wide.
- **A3** An all-grey palette only where the build writes that palette from it.
- **A4** Encoder options live beside their assets; a recipe may carry a sprite shape in its name.
- **A5** No JSON: tables are TSV.
- **A6** Each edition combines its catalog, character map, fonts, metrics and layout with its measured code differences; differing resources are chosen in their owning module or build rule, and editions that agree are grouped. _Check: make compare-editions._

### Compilers

The set is frozen: three C generators built from the pinned `alchemy-gcc` submodule, six profiles, no research and no new compiler, option, route or alchemy-gcc commit. The one exception is a host fix that leaves every compile of the twelve editions byte-identical. Matching shows practical compatibility, not Camelot's exact compiler.

- **K1** Game Thumb C: alchemy-gcc (GCC of 2000-07-31) with `-O2 -mthumb -mcpu=arm7tdmi -nostdinc -fcall-used-r4`, plus `-mthumb-interwork` for ☀️ and K2's options for ⚓️; libgcc C with `-O2 -mthumb -mcpu=arm7tdmi -fno-inline`. ARM C: GCC 2.95.2 with `-O2 -mthumb-interwork -fomit-frame-pointer -fcall-used-r4`. Sound and flash: pret's `old_agbcc` (`-O2` and `-O`, `-mthumb-interwork`). The Makefile's SOUND_C, FLASH_C and ARM_C are the only routes; `make modern` adds none.
- **K2** ⚓️ adds, for every Thumb file, `-mthumb-split-constants`, `-mthumb-call-via-lr` and the stock `-mtune=arm9tdmi`, habits measured across its whole code; no other scheduler or allocator change. An instruction-order mismatch alone is no reason to change compilers.
- **K3** A compiler change needs one option set that explains most of a game's code, no public compiler of the time that already does, a plausible Camelot-style change with its evidence recorded here and in alchemy-gcc's README, and Pascal's approval.

### Work

- **W1** A plain Makefile whose every rule can be read; a build tool is a small tested C program for a step make cannot do; Rust only in the optional Alchemy Devtools; no TypeScript, JavaScript, Python or shell beyond a command line; tooling nothing needs is removed.
- **W2** Work on a branch; `main` is the only long-lived branch; land with `make land`.
- **W3** The Makefile owns compiling and linking, `tools/` the C encoders and small tools (`ags-` prefix), Alchemy Devtools the matching aids and count. Follow pret where it settles a question, and never be stricter: far-call banks are pinned per edition in the linker scripts; packer leftovers are tagged literal bytes beside their asset; each encoder takes one rule for all its streams, and a stream Camelot edited after packing takes a patch file of measured literals.
- **W4** Match first what other unfinished code calls, with the structures it shares, then the largest with nothing left to name.
- **W5** Before every commit, `make compare-editions` prints OK for all twelve editions. A tree that merges other branches does so from a clean build (`make clean` first) before it lands, since an object one branch built can hide another's change.
- **W6** A change to what counts, a rule, an option or routing lands as its own commit with DONE before and after.
- **W7** Parallel work divides by owner; check a name is free (`git log --all -S`) before using it; when branches merge an adoption wins over edits to its draft; commit only verified work.
- **W8** Humanizing follows H2 toward H4 and keeps every edition byte-identical; message names stay linker symbols.

## What matching has measured

Not rules; facts about alchemy-gcc that keep coming back.

- `p[n]` and `*(p + n)`, and `&p[n]` and `&*(p + n)`, can compile differently: each site keeps the spelling it matches with.
- A struct object declared before its type is complete keeps a smaller alignment and changes the code that reads it: a header includes its structs' headers first.
- alchemy-gcc pads every struct to 4 bytes, and a field after the first is addressed from the table's base: a table read by columns is a `[][N]` array with an `enum` naming the columns.
- Locals declared in an inner block take their pseudos later and change register allocation.
- A loop built from labels and `goto` has no loop notes: loop.c neither hoists its constants and addresses nor strength-reduces it nor deletes it when empty, jump.c does not copy its exit test, and global.c does not weight its references. Its C form rarely matches, and an empty C loop is deleted.
- A file that tests `LANGUAGE` without including `edition.h` silently gets the Japanese branch.
- Within one object, code and data follow definition order after preprocessing; only the object list orders objects. Every Thumb function starts on 4 bytes, so code shows no object boundary; data can, through a gap no type alignment explains.
- Register choice is arithmetic: allocation order r3, r2, r1, r0, ip, lr, r4 to r7, r8, r10, r9, r11; global.c ranks pseudos by refs and live length, loop depth weighting refs. A constant `REG_EQUAL` note doubles a pseudo's live length.
- An empty asm counts 4 estimated bytes when arm_reorg places literal pools, and emits none. A one-pass block's loop-end note ends CSE's block and is a scheduling barrier; sched2 breaks ties by RTL order. A halfword constant that survives to a register loads from the pool.
- CSE reuses a register holding 0 or 1, so a native store of a register is often a constant in the source. Unused locals do not make frame gaps; allocation does.
- Japanese is often an older layout of a function with its own `#if`, or stays on its scaffold. Nested functions adopt with their parent. A function that saves r9 and never uses it is a nested function storing its static chain.
- ⚓️ near misses: of 796 drafts, 400 differ only in instruction order and 48 only in register choice; the native most often issues a literal-pool load earlier than alchemy-gcc. That corpus is where a K3 question about ⚓️'s scheduling would start. Another row recurs: after a store, the native puts some other instruction (often the second half of a constant) before a load through a different base, where alchemy-gcc issues the load at once; no single barrier reproduces it. A one-pass block holding the statement before a pool load and the assignment that needs it can move the load up (BattleEffect_UpdatePairedArcSpawner).
- To measure a rewrite in seconds, compile its one object to assembly for one edition with the Makefile's command and diff it against a baseline with `.L` label numbers ignored; then `make compare-editions`.
- Builds from another branch leave `out/*/deps.mk` and `out/*/objects.mk` that break this one: delete them. After switching to a branch whose tools differ: `rm -rf tools/out/obj tools/out/ags-* && make tools`. In zsh, a variable holding several flags is one word unless written `${=VAR}`; `git grep -E` has no `\b`, so use `-w`.
