# Alchemy

This file instructs the agents that help people build with Alchemy: change the game, add to it, read it. People read `README.md`. The agents keep this file current, wording included. Rule letters are kept, so old citations resolve. Alchemy rebuilds Golden Sun: **The Broken Seal** (☀️, build `tbs`) and **The Lost Age** (⚓️, `tla`) byte for byte from readable C, assembly and editable assets, in Japanese, English, German, Spanish, French and Italian: twelve editions, `tbs-ja` to `tla-it`. Japanese releases are the source editions; localizations are measured differences. Both games build byte for byte from this repository.

## Where things are

- `games/<game>/src`, `include`, `sound`, `text`: each game owns its copy of what it uses. ☀️'s code sits in one folder per bank, grouped by the credits' divisions, with a scene's overlay one file; `games/tbs/src/README.md` maps the folders, and each object's header has the same path under `include/`. ⚓️ has the same shape: every scene is one C file in `src/scene` (the debug rooms in `src/debug`), code several overlays keep a copy of is in `src/scene/shared`, one header a routine (`#include "shared/cracked_tile_crack.h"`), and each bank's joined object is `<object>.c` with its parts beside it as `<object>_<part>.c` and a private `<object>_internal.h` (`src/field/field.c` and `src/field/field_actors.c`), its headers in `include/<bank>/` as ☀️'s are; `games/tla/README.md` and each folder's README map them.
- Each game links from one linker script, `games/<game>/ld_script.ld`, run through the C preprocessor with the edition defined as its C is: it lists every object of the main image in link order, and includes `games/<game>/src/system/overlay/overlay.ld`, one block per overlay, when the build defines `OVERLAY`. Both games' scenes and debug rooms define their globals in C, those that must keep the ROM's order (rather than the linker's for common symbols) marked `BSS_DATA` (`macros.h`, as pret's `EWRAM_DATA`; ⚓️ marks them all), which the compiler emits in the order the file first declares them, an `extern` before it or in a header it includes counting, with `ALIGNED(n)` where the ROM spaces them wider than their types; in each game only the title's, which start on a halfword, are `src/scene/title_bss.s`. In both games a scene links the entry table scenes share, `src/scene/entry.s` (⚓️ keeps its own in `src/scene/entry/` for a few scenes whose routines are named otherwise; every ☀️ scene and debug room names its six slot routines `Scene_Initialize` to `Scene_GetExitRegions` and links the one table), and an import table the build writes for each overlay from `src/system/overlay/imports.inc`, the far-call stubs its code calls in the list's order; the maps are one object, `src/map/maps.s`, including each map's `map.inc`; `overlay.ld` writes the usual scene block as `SCENE(name)` or `SCENE_WITH_BSS(name)`, and ☀️'s writes every block through its macros (`SCENE_AND(name, part)` for a part linked after the scene's code, `DEBUG_ROOM(name)`); assembly that another file includes, rather than the linker script listing it, is `.inc`; and an alignment the ROM gives a scene's globals is `ALIGNED(n)` at the first of them, never `ALIGN` in a script. Code several scenes keep a copy of is `src/scene/shared/<name>.c`, included at its place in the ROM; a header holds only declarations, inline helpers and macros. Each game's C takes one include path, `games/<game>/include`, and names a header by its folder (`"field/event.h"`); a header lives only there, a scene's own declarations are in its `.c`, and under `src/` only a joined object's private `<object>_internal.h` remains.
- An overlay reaches a main-image routine `X` through the far-call export `XFar` (`src/gamepak/far_call/*`) and its own veneer to it, named `X` (the line `export X, XFar` in `src/system/overlay/imports.inc`, from which the build writes each overlay's table); a placeholder veneer is renamed once its target is named. A second row for one target (`Import_` and the address names left in `imports.inc`) is a veneer whose calls differ from the target's prototype or whose place in the list shapes an overlay's table; where neither holds, the overlay calls the target by its own name and the row goes.
- The docs start at `games/README.md` and `games/tbs/README.md`; a folder's README is its page, a subject that spans folders has a guide beside the game's README (`field.md`, `battle.md`, `interface.md`, `system.md`, and ⚓️'s `sequel.md`), and `games/tbs/glossary.md` defines the words. The site, <https://alchemy.pascalpixel.com/>, is built from them in `alchemy-docs`.
- The `Makefile` builds everything; `tools/` holds its small C programs (`ags-*`). `out/` and `tools/out/` are build output.

## Commands

```sh
make                   # tbs-en, the compilers and tools first, once (make bootstrap: those alone)
make compare-tla-de    # one edition (tbs or tla, then ja en de es fr it) against rom.sha1; make tla-de builds it
make -j8 compare-tbs   # the six ☀️ editions; compare-tla for ⚓️'s
make compare-editions  # all twelve
make modern            # both games' C with a current GCC (MODERN_CC): no errors
make test              # the build tools' tests and the format check
make SHIFT=4 tbs-en    # the shift test: everything after the header moves 4 bytes, into out/shift-4/
```

Setup is in `README.md`, and `make help` lists the rest. `make compare-editions` prints a lot: send it to a log file and count the `: OK` lines. After switching branches, delete `out/*/deps.mk` and `out/*/objects.mk`; after renaming sources, delete the editions' `out/` folders; after switching to a branch whose tools differ, `rm -rf tools/out/obj tools/out/ags-* && make tools`. After changing which main-image routines a ⚓️ scene calls, delete that edition's `obj` folder before believing a compare: an incremental build has passed a ROM whose overlay import table a clean build refused (13 November 2026).

## Your game or this repository

A change in your own game may move bytes freely: it no longer matches `rom.sha1`, and `compare` says so, as it should. Please don't share built ROMs, original or modified (L1). A change sent back to this repository keeps every edition byte-identical (W5): `make compare-editions` prints OK for all twelve, `make modern` and `make test` pass. Where such a change moves bytes, it is reshaped in source until it does not. Open an issue first for any compiler, option or routing change, or for deleting what cannot be restored.

## Marks in the source

Marks that say where the source is shaped by the original ROM rather than by what the game needs. In your own game each is a place you may simplify; a change sent back here keeps them true:
- `FAKEMATCH(<kind>)`: a form kept only so the old compiler emits the original's code, with a few words saying what it is. Its plain form does the same thing: write that in your own game. The kinds, worst first: `signature` (a type that is not the real one), `volatile` (on what no hardware or interrupt shares), `barrier` (an empty asm), `wrapper` (a call layer with no purpose of its own), `temporary` (a local that only stands for another value), `dead` (a statement that changes nothing). Neither game takes a register pin, nor ☀️ a `signature`: `check tags` refuses them, and prints each game's fake-match score, the kinds weighed as alchemy-devtools' S2 weighs them.
- `LEFTOVER(<kind>)`: Camelot's own code that does nothing in this edition but still shapes its bytes: an unused local (`frame`) or an idle shape copied from sibling routines (`template`). Safe to remove in your own game.
- `// DEAD:`: code whose instructions the ROM keeps and that cannot change the result (S3).
- `// BUG:` and `BUGFIX`, `// UB:` and `UBFIX`: the original's bug or undefined behaviour, kept, with its fix behind the option; build with the option to take the fix.
- `VIEW(<part>)`: a part of a joined object that sees a name otherwise than the rest; unfinished.
- `XXX:`: an open question at the code, with what would settle it.
- `CAMELOT_ASM("proof")`: a helper Camelot wrote in assembly, kept as assembly inside C.

## Legal

- **L1** Never commit, upload or publish a ROM, private inputs or any copy of the game files. The cartridge logo lives only in `ags-header`, as in pret's gbafix.
- **L2** Evidence is our own ROMs, this repository and public documentation; never another project's Golden Sun work.
- **L3** Never use, open, read or mention leaked Nintendo or Camelot code or SDKs, or anything derived from them.

## Source

- **S3** Source is readable modern C in English, as pret writes its games:
  - Layout: lowercase short file names, the same folders in both games, code in its bank's folder, a function in the module of its linker neighbours. An object over about 3,000 lines holding several families may be written as parts with a private `<object>_internal.h`, included in ROM order: each game names each part `<object>_<part>.c` beside its object, as pret names its files (`battle/battle_turn.c`); a scene's overlay is one file: a routine of another bank that Camelot linked into a scene's middle is included at its place (`#include "../field/field_effect_move.c"`), and a scene's data its overlay places after an image or a tile sheet is `LATE_DATA` (`.data.late`, placed by `overlay.ld`). A scene's file opens with its one list of includes; what only that scene reads is in its file, and what several scenes share is in `src/scene/shared/` (a header, or a `.c` included at its place).
  - Language: C89 with the compilers' GNU extensions; types, signedness and scopes from the game's code; data read through structs and enums rather than offsets and casts wherever a match allows.
  - Naming: functions `Module_PascalCase`, globals `gName`, statics `sName`, constants and macros `UPPER_SNAKE_CASE` (a macro that stands for a call is named as a function, as the plain `Actor_SetPosition` over `Actor_SetPositionFX` is), locals and fields `camelCase`; words spelled out except the abbreviations a programmer reads without stopping; an acronym is a word in mixed case and capitals in constants, as GBATEK writes them. `wait()` is the lowercase primitive. The fixed-point, angle and matrix names follow Sega’s SGL reference: `toFIXED`, `DEGtoANG` and the `FX` suffix in its own spellings, and ours modelled on its names (`INTtoFIXED` and `FIXEDtoINT` on its `toFIXED`, `Matrix_RotateX` on its `slRotX`); the m4a driver keeps its own. An unknown stays a placeholder (`sub_08012345`, `unk_14`).
  - Vocabulary: one name per concept, and each word in one sense, as `glossary.md` defines them. The reader is a modern engineer who knows the Game Boy Advance and a player who knows Golden Sun in English: a word is right when they follow it without a gloss. A word is chosen, in order: the game's English text, for what the player sees; the term such an engineer already uses (a sprite, a sprite sheet, a texture, a frame; for the console's own registers and fields, GBATEK's name); plain English. What a thing is comes from the sources: the game itself (its English and Japanese text, its debug labels, its credits), Sega's SGL manual, GBATEK. Each glossary entry ends with a Sources line saying what each of the three calls the thing. The sources are cited, but they do not choose the word: a word of the game's makers or of SGL's is kept only where it is also the word the reader would use. Never another decompilation's word. An event calls a command by its name in `event.h` (`Actor_FaceDirection`, `Event_ShowMessage`); the main-image routine's own name is written in a scene only where that site compiles differently through the inline. The settled words are the glossary's.
  - SGL: the fixed-point, angle and matrix code is named after the reference of Sega’s Saturn library (1997), where its design matches: `FIXED` numbers with an integer and a decimal part, `toFIXED()`, the `FX` suffix (`Math_MulFX`, `Math_SqrtFX`), angles of 65,536 to the turn written `DEGtoANG(90)`, a 4×3 current matrix, and `Matrix_Push`, `Matrix_Pop`, `Matrix_RotateX`, `Matrix_Translate`, `Matrix_Scale`, `Matrix_LookAt` and `Trig_Atan(x, y)`, ours after its `slPushMatrix`, `slPopMatrix`, `slRotX`, `slTranslate`, `slScale`, `slLookAt` and `slAtan`. A 16.16 number has the type `FIXED` (`typedef s32 FIXED;` in each game's `fixed_math.h`) wherever a member, parameter, result or local holds one, and a `MATRIX` is twelve of them, in our code the rotation's nine and then the translation's three, its fourth row (`system/matrix.h`). It matches in these respects: the arctangent takes (x, y), a push copies the current matrix, and the fixed-point square root has 8.8 precision. It differs in these: the matrix stack is one level deep, the sine table is coarser and rounds, the look-at has no roll, and the random numbers are the C library’s. The names are borrowed for the same designs; nothing here says the code comes from SGL, which cannot run on this console. `INTtoFIXED` and `FIXEDtoINT` are ours, in its style; the task system, `wait()`, the hardware names and the integer types are not taken from it.
  - Numbers stay numbers until evidence gives them a meaning; then they have a name (an enum or macro in a shared header), and neither code nor comments use the number again. A number is decimal, or composed (`240 * 160`, `toFIXED(4) / 5` when exact, `DEGtoANG(45)`, `DMA_COPY_WORDS(n)`, `RGB(r, g, b)`; a fraction of a pixel quantity, a position, speed, gravity or distance, is `toFIXED(n) / d`, and `FIXED_ONE * n / d` is only for a unitless factor, a scale, decay, bounce or ratio); hex is kept only where a programmer of the period wrote hex: flag numbers (Camelot's debug flag editor shows them in hex), hardware addresses, register values and bits, masks and packed fields, values from `0x80000000` up, and the m4a driver's stock tables. Nothing else stays hex: a layout offset is a struct field, an all-ones marker has a name or is `-1`, a one-less bound is `n - 1` or its decimal, a 16.16 value is the `toFIXED()` of the short decimal that compiles to it (`toFIXED(0.3)`, as SGL's samples write them), and a stored byte nothing explains yet is a placeholder to settle, not a form to keep. A call or table row takes plain pixels and plain decimal speeds (`Actor_SetPosition(ACTOR_MIA, 880, 502)`, `Actor_SetSpeed(ACTOR_STATUE, 0.8)`), converted to 16.16 inside its definition by `toFIXED()`, which multiplies so that a negative is never shifted. A live 16.16 value goes through its `...FX` form (`Actor_SetPositionFX`), as SGL names the fixed-point form of a routine; a macro that reads each argument once may take live plain pixels (`Actor_SetPosition(actorId, x, z)`), and the macros that read one twice (`Actor_SetSpeed`, `FieldCamera_SetSpeed`, `FieldCamera_MoveTo`, `MapGrid_SetShake`, `ShipRooms_MoveCameraAndWait`) take only constants. `toFIXED()` turns whole pixels, a constant or a live value (`toFIXED(leader->x.part[0].integer)`), into 16.16 only in arithmetic, comparisons and assignments on a stored 16.16 value; `INTtoFIXED()` is the plain shift, kept where `toFIXED()` on a live value would move bytes, and `FIXEDtoINT()` is the way back. A coordinate’s halves are its `integer` and `decimal` parts. Flags and sounds come from `flags.h` and `sounds.h`; a scene's temporary flag is named beside its includes.
  - Original behaviour: undefined behaviour keeps its form behind `UBFIX`; a bug keeps its code with `// BUG:` and a fix behind `BUGFIX`; `// DEAD:` marks code whose own instructions the ROM keeps and that cannot change the result, and says what the ROM keeps: `// DEAD: <what>; the ROM keeps <its instructions>.` Unreachable things open their comment with `Unused:`; a function nothing refers to is `UNUSED`. A comment says what the code does for the game; how the compiler came to emit it (registers, passes, instruction counts) is not written in this repository.
  - Editions: C and the linker scripts compare `edition.h` and `version.h` values; only plain assembly and `.S` files use edition names. `LANGUAGE` chooses only what language decides: text, message ids, fonts and glyph widths, and layout that fits the text. Every other difference between editions (a fix, a changed rule, value, check, timing or table) is a patch level from `version.h` (`TBS_PATCH_n`, `TLA_PATCH_n`), combined when no single level selects its editions (German alone is `PATCH_2 && !PATCH_3`). A value that differs by edition is one named macro chosen at the top of its file. A test is written bare, `#if LANGUAGE != LANGUAGE_JAPANESE`, `#if LANGUAGE == LANGUAGE_SPANISH || LANGUAGE == LANGUAGE_ITALIAN`, `#if TBS_PATCH_2 && !TBS_PATCH_3`.
  - Macros: a macro that makes more than one call is a comma expression; wrapped in `do { } while (0)` it compiled differently in every ☀️ edition (10 November 2026).
  - Formatting: clang-format's LLVM style (`.clang-format`); header guards are `ALCHEMY_<NAME>_H` (in ☀️ every header has one, NAME its file name, a far-call bank header's `FAR_CALL_<NAME>`). The formatter leaves include order alone, since a joined object includes its parts and a scene its shared code in ROM order; ☀️'s leading headers are in one order by hand: the file's own header, the game-wide ones of `include/`, the bank headers by path, then the build's (`text/msg_ids.h`).

## Assets

- **A1** The build is as plain as pret's: C, assembly, indexed PNGs with real palettes, WAV, MIDI, PO text, one `map.txt` (its grid) and one `scene.tsv` (its points, entrances and bounds, the header computed) per map, and TSV only for a table an encoder packs; never raw dumps, blobs or stored compression tokens. Two named exceptions exist only so the original ROMs come out byte for byte, and your own game needs neither: a packing patch (`*_patch.tsv`) has the packer read one byte where the asset has another, and the `PACKER` lines in each game's `overlays.s` are what Camelot's writer left after a packed overlay, which no program reads. Neither grows. Each asset builds beside its source, ignored by git.
- **A2** An image is drawn the way the game shows it: sprite sheets and tile sheets at their real width or sprite shape, tilemapped images as the map shows them, animations one frame wide.
- **A3** An all-grey palette only where the build writes that palette from it.
- **A4** Every file an encoder reads is a prerequisite: one Makefile rule per kind of asset, with the encoder listing what else it read in a `.d` file beside its output.
- **A5** No JSON, apart from `.recomp.json` and `.recomp-2.json` at the root, one per game, which recomp.fyi reads and nothing here does. A table the code reads as it stands is a C array at its place in the ROM, read through its struct with designated initializers and a comment naming each entry from the game's text; where a C object cannot start where the ROM's does (one holding words starts word-aligned), the table sits among pictures in a data file, or a row holds a scene or resource id in a halfword (the ids are link-time symbols, which the compiler cannot place in one), its rows are that file's assembly, as pret's `data/*.s` are: one macro a row, a scene or resource by its name, and a flag or sound by its C name from `enums/<header>.inc`, which the build writes from the header's enums and its macros that are one number. No table is an incbin of a TSV; `ALIGNED(n)` (macros.h) gives an array the ROM's alignment.
- **A6** Each edition combines its text, fonts and layout with its measured code differences; differing resources are chosen in their owning module or rule.

## Work

- **W1** A plain Makefile whose every rule can be read; a build tool is a small tested C program; no Rust, TypeScript, JavaScript, Python or shell beyond a command line; tooling nothing needs is removed.
- **W3** Follow pret where it settles a question, and never be stricter.
- **W5** Before every commit, `make compare-editions` prints OK for all twelve editions. Builds are incremental, as pret's are; CI builds every push from a clean clone.
